## In-Scope — 사용자 제공 공통 계약

- 하나의 프록시 주소, 제출 백엔드 1개와 조회 백엔드 A·B 총 3개.
- `POST /api/submissions` → 제출 서버에만 전달. 본문 바이트 보존.
- `GET /api/submission-status` → 조회 A·B 중 하나. 한 요청은 한 곳에서 처리, 합의한 묶음에서는 양쪽 모두 사용.
- 경로 재작성 없음. 상태·전달 대상 헤더·바이너리 응답 보존.
- 즉시 연결 거절 502, 요청 수신 후 무응답 제한 초과 504.
- 이미 응답을 시작한 뒤 실패하면 새 HTTP 오류 응답을 덧붙이지 않는다. 불완전 응답을 클라이언트가 판별할 수 있어야 한다.
- 장애 반복 뒤 정상 서비스 및 FD 회수.
- 기존 정적·동적 서빙과 HTTP 처리 회귀 유지.
- C/표준 C/POSIX로 서버 구현, 테스트 백엔드는 Python 허용.

## 개인 초안 결정 (사용자 승인)

- 라운드로빈·재시도 없음. 유효한 조회 본문 수신 완료 후 A/B를 선택하며 실패해도 다음 순번으로 이동한다.
- CLI: 기존 `<port>`는 로컬 서빙 유지. `<port> <submission-ip:port> <status-A-ip:port> <status-B-ip:port>`로 프록시를 켠다.
- 숫자 IPv4만 사용. 연결·백엔드 송수신 무진행 제한 1초, 클라이언트 수신·송신 제한은 기존 정책 유지.
- 요청은 기존 64KiB 상한으로 전부 받은 후 중계. 응답만 스트리밍한다.
- 응답 길이 명시/청크/EOF 지원. EOF 방식은 클라이언트에 chunked로 재프레이밍한다. 깨끗한 EOF와 원 서버의 의도한 조기 종료는 길이 정보 없이는 구별할 수 없다.
- 클라이언트 요청 chunked·keep-alive·Upgrade는 추가하지 않는다. 표준 문법을 만족해도 미지원 응답 전송 코딩은 502.
- 명시적 응답 길이와 TE 동시 존재·중복 CL은 엄격히 502. 종료 청크는 정상 완료 후에만 생성한다.
