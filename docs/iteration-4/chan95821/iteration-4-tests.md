# Iteration 4 Reverse Proxy 개인 테스트 기준

상태: 검증 기준 + 개인 실행 결과(2026-11-24). [개인 요구사항](iteration-4-requirements.md)의 동작을 확인하기 위한 문서이며 팀 공통 채택 기준은 아니다.

## 1. 정상 라우팅·중계

| 조건 | 통과 기준 |
| --- | --- |
| 제출 API에 쿼리와 바이너리 본문 전송 | 제출 서버만 요청을 받는다. 요청 대상·본문 바이트, 원본 `Host`와 전달 대상 헤더가 보존된다. |
| 정상 조회를 다른 요청과 섞지 않고 연속 4건 전송 | 요청마다 A·B 중 한 곳만 처리한다. 첫 서버가 어느 쪽이든 이후 A·B가 교대한다. |
| 등록된 프록시 경로에 맞지 않는 GET·POST 전송 | `405`와 맞는 `Allow`가 반환되고 백엔드 요청은 없다. |
| `/api/hello` 및 기존 카페 데모와 CGI 확인 | 부모 이슈의 `/api/hello` 중계 조건과 기존 정적·동적·CGI 회귀를 모두 통과한다. |

## 2. 단위 테스트 — 요청 파서의 헤더 제공

[`request_header_order()`](../../../tests/unit/test_http_parser.c)는 `http_parse_request()`로 파싱한 뒤 `http_header_next()`로 다음 계약을 확인한다.

- 일반 헤더와 `Host`·`Connection` 모두 수신 순서대로 읽힌다.
- `X-Demo`와 `x-demo`는 합치지 않고 별도 줄로 남긴다. 값의 양끝 공백은 제거하되, 빈 값도 헤더 한 줄로 반환한다.
- 마지막 헤더 다음에는 순회가 끝난다. 이름은 수신 버퍼를 참조하며, 입력 바이트는 바뀌지 않는다.

실행: `make test_http_parser && ./build/test_http_parser`. 전달·제거 판단은 이 단위 테스트의 범위가 아니다.

### 라우트 핸들러의 공통 프록시 호출

제출·조회 핸들러는 기존 `router_handler` 시그니처로 호출된다. `proxy_config_init(NULL)`이 확정한 기본 설정과 원래 요청·응답 객체를 `prepare_proxy_response()`에 한 번 넘긴다. 조회 그룹 상태는 설정 저장소에 있어 호출 간 유지된다. 이 테스트는 호출 경계만 검증하며 실제 중계는 별도 검증한다.

`http_select_handler()`를 통해 정확한 경로·메서드가 각 핸들러로 연결되는지 먼저 확인한다. 메서드가 다르면 `405`와 `Allow`, 경로 뒤에 하위 경로가 붙으면 `404`를 반환하며 두 경우 모두 핸들러를 선택하지 않는다.

### 라우트 선택 후 사전 검증

라우트에 등록된 선택적 검증 함수는 매칭이 성공한 뒤 실행한다. `Connection`의 여러 줄 중 하나라도 요청의 `Host`, `Content-Length`, `Transfer-Encoding`을 지목하면 프록시 경로는 `400`을 반환하고 핸들러를 제공하지 않는다. 일반 헤더 지목은 허용한다. 기존 경로에는 이 정책을 적용하지 않고, 경로·메서드 불일치의 `404`·`405` 판정은 검증보다 우선한다.

### 백엔드 요청 헤더 작성

`build_proxy_request_headers()`는 원본 요청 대상과 `Host`, 전달 대상 헤더의 순서를 유지한다. 여러 `Connection` 줄이 지목한 일반 헤더와 이미 처리한 `Expect`는 제외하고, 다음 연결용 `Via`·`Connection`·필요한 `Content-Length`를 작성한다. 필수 헤더가 지목되거나 출력 버퍼가 부족하면 전송 가능한 길이를 반환하지 않는다.

### 공통 프록시의 상위 실행 흐름

`prepare_proxy_response()`는 요청 헤더를 먼저 작성하고, 성공한 경우에만 백엔드 연결 확보 단계로 진행한다. 직접 호출했을 때도 필수 헤더 지목은 `400`으로 처리한다. 설정이 없거나 후보가 없는 업스트림은 `500`으로 처리한다. 헤더 작성 실패 시 백엔드에 연결하지 않는다.

## 3. 헤더·본문 경계와 실패 처리

### 백엔드 응답 헤더 수신 경계

요청 수신과 백엔드 응답 수신은 공통 `receive_http_headers()`로 `CRLFCRLF`까지 읽는다. 전체 수신 길이와 헤더 끝 위치를 따로 반환해 함께 도착한 바이너리 본문을 보존한다. 백엔드 헤더 단계에서 조기 EOF·수신 상한 초과는 `502`, 수신 제한 초과는 `504`다. 최종 응답 헤더 대기 제한은 검증 기본값 3초이며, 연결·요청 송신·본문 무진행 제한 1초와 구분한다. 이 단계의 단위 테스트는 상태 줄·헤더 의미 해석이나 최종 응답 중계 완료를 증명하지 않는다.

### 응답 헤더 해석과 중계 가능 여부

`http_parse_response_headers()`는 입력을 변경하지 않고 상태 코드·Content-Type·길이·전송 형식을 해석한다. 일반 헤더 문법과 Content-Length 숫자 검증은 요청 파서와 공유한다. 중복 길이·잘못된 상태 줄·제어 문자·접힌 헤더는 `502`다.

`validate_backend_response_headers()`는 유효한 HTTP 응답 중 이번 프록시가 중계할 수 있는 범위를 판정한다. 본문 허용 최종 응답에는 Content-Length가 필요하고 Transfer-Encoding은 미지원이다. 정상 형식의 `404`·`500`은 허용한다. `204`·`304`는 길이가 없어도 허용하지만 `204`의 Content-Length와 1xx의 길이/전송 선언은 거부한다. `101`은 미지원이다. Connection이 길이 헤더를 지목해도 거부한다. 중간 1xx가 유효하다는 판정과 최종 응답까지 계속 수신하는 동작은 구분해 검증한다.

### 응답 헤더 전달

`prepare_backend_body()`는 백엔드 응답 헤더 중 hop-by-hop, `Connection`이 지목한 필드, 다시 작성하는 `Content-Length`·`Content-Type`을 제외한 나머지를 원본 순서와 다중 줄 그대로 `router_response.headers`에 담는다. `send_response()`는 상태 줄·`Content-Type` 뒤, 길이·연결 헤더 앞에 이 블록을 한 번만 보낸다.

- `Location`, `Cache-Control`, 여러 줄 `Set-Cookie`가 보존되고, `Connection`이 지목한 헤더는 전달되지 않는다.
- 준비된 헤더가 없는 기존 핸들러의 응답 형식은 바뀌지 않는다.
- E2E는 백엔드가 붙인 `X-Mock`·`Cache-Control`이 클라이언트까지 도달하는지, `/api/hello`의 이진 본문이 바이트 단위로 일치하는지 확인한다.

### 백엔드 본문 공급자

`prepare_backend_body()`는 헤더와 함께 읽은 본문을 응답 소유 저장소로 옮기고, 나머지 본문은 백엔드 소켓에서 읽는 공급자를 준비한다. 헤더 수신 함수의 스택 버퍼가 사라진 뒤에도 `Content-Type`과 동반 본문을 사용할 수 있어야 한다.

- 헤더와 본문이 한 번에 도착해도 선언 길이만큼 정확히 한 번 중계한다. 헤더 뒤에 늦게 도착한 본문도 이어서 읽는다.
- 선언 길이보다 짧게 끝나면 공급자는 `BODY_ERROR`를 반환한다. 선언 길이를 넘는 여분 바이트는 중계하지 않는다.
- 본문 없는 `204`·`304`는 길이 0으로 준비하며 읽기를 시도하지 않는다. `Content-Type`이 없으면 `application/octet-stream`을 쓴다.
- 정상 완료·조기 종료·중계 실패 어느 경우에도 공급자 정리는 백엔드 FD를 닫고 메모리를 해제한다.
- 중간 `1xx`를 최종 응답으로 잘못 중계하지 않도록, 최종 응답 수신 루프가 구현되기 전에는 `1xx`를 `502`로 거부한다.

### 백엔드 요청 송신

`send_proxy_request()`는 헤더 뒤에 본문을 바이너리 안전하게 전부 전송하고 성공 시 0을 반환한다. 빈 본문도 허용한다. 작은 송신 버퍼로 부분 송신을 유도해 바이트 순서를 확인한다. 읽지 않는 상대에 대한 송신은 총시간 제한으로 `504`, 종료된 상대는 `502`다. 모든 경우에 FD 소유권은 호출자에게 남는다. 공통 송신 루프는 기존 클라이언트 송신에서도 사용하며 기존 회귀 테스트를 유지한다.

- **헤더 선별:** `Connection`이 지목한 일반 헤더는 표기나 순서에 관계없이 양방향에서 제거된다. 지목되지 않은 전달 대상 헤더와 바이너리 응답 본문은 보존된다.
- **조기 거부:** 요청의 필수 헤더가 `Connection`에 지목됐으면 `400`을 반환한다. `Expect: 100-continue`가 있어도 `100 Continue`나 백엔드 연결이 발생하지 않는다.
- **백엔드 응답:** 정상 형식의 `404`·`500`은 그대로 중계한다. 지원하지 않는 본문 형식은 최종 응답 전 `502`, 최종 헤더 대기 제한 초과는 `504`다. `204` 응답에는 본문을 보내지 않는다.
- **바이트 경계:** 백엔드 응답 헤더와 본문 시작이 같은 읽기에 들어오거나 여러 번에 나뉘어 들어와도 본문 손실·중복이 없다. 읽기 경계는 단위 검증에서 통제하고, 실제 프로세스 검증에서는 최종 바이트 일치를 확인한다.
- **전송 중 실패·정리:** 선언 길이보다 짧게 끊기거나 본문 수신이 제한 시간 동안 멈추면 연결을 닫고 두 번째 HTTP 응답을 붙이지 않는다. 장애를 반복하고 연결 정리가 끝난 뒤 열린 FD가 누적되지 않으며 다음 정상 요청이 처리된다.

## 4. 조회 서버 종료·복구

### 한 서버 연결과 공통 I/O 유틸

- `connect_backend()`는 숫자 IPv4·IPv6 주소만 받는다. DNS 이름이나 잘못된 주소·포트는 설정 오류 `500`이다.
- 실제 로컬 리스너에 연결하면 호출자 소유 FD와 0을 반환한다. FD는 `FD_CLOEXEC`이며 다음 송수신을 위해 blocking 모드로 반환한다.
- 리스닝하지 않는 로컬 포트는 `502`와 FD -1을 반환한다. 연결 대기는 검증 기본값 1초로 제한하며 초과 시 `504`다. 실패한 소켓은 내부에서 닫는다.
- 공통 유틸은 읽기·쓰기 준비 대기와 이미 지난 마감 시각의 `ETIMEDOUT`, FD 상속 방지를 별도로 확인한다. 연결 대기 결과를 대역 처리한 테스트는 `504`·FD -1과 실제 시도 소켓의 닫힘을 확인한다. 이는 실제 네트워크가 응답하지 않는 조건의 타임아웃 검증과 구분한다.

**선택 단위 테스트:** `select_round_robin_backend()`는 두 후보를 번갈아 고르고, 제외된 후보를 건너뛰며, 선택 가능 후보가 없으면 실패를 반환한다. 제외된 후보가 다시 선택 가능해지면 선택 대상에 포함한다. 연결이나 시간 대기는 이 단위 테스트의 범위가 아니다.

**연결 확보 단위 테스트:** `acquire_proxy_backend()`의 한 서버 연결 함수만 대역으로 교체한다. 고정 서버는 한 번만 시도하고, 조회는 첫 연결 실패 시 다른 후보에 한 번 우회한다. 제외 중인 서버·이번 요청에서 실패한 서버를 다시 고르지 않는다. 제외 만료 후 해당 서버에 연결이 성공하면 제외 상태를 해제한다. 내부 오류는 장애 서버로 기록하지 않으며, 후보가 없으면 연결하지 않고 `502`를 반환한다. 성공한 실제 테스트 FD는 호출자가 닫는다. 이 테스트는 TCP 연결 자체의 검증이 아니다.

**선택 정책과 연결 결과 통보:** 제외 만료 시각과 라운드 로빈 순번은 선택 모듈이 관리한다. 공통 연결 함수는 선택된 인덱스·연결 결과를 `on_connection_result`에 전달하며 제외 배열을 직접 변경하지 않는다. 정책 단위 테스트는 제외 중 후보 건너뛰기, 요청별 재시도 금지 반영, 연결 장애 시 제외·성공 시 복귀·내부 오류 시 상태 유지와 순번 선택을 확인한다. 결과 통보가 내부 오류로 끝나면 이미 확보한 FD를 닫고 `500`을 반환한다.

1. A·B의 정상 교대를 확인하고 B 차례에 B가 종료된 상태로 조회한다. B 연결 실패를 처음 만난 조회도 A가 살아 있으면 성공하고, 요청은 A에서만 처리된다.
2. 일시 제외 구간에는 조회가 A로만 가며 B에 새 연결을 시도하지 않는다. **응답의 서버 식별자만으로는 B에 연결을 시도하지 않았음을 증명할 수 없으므로**, 테스트 관측 지점에서 백엔드별 연결 시도도 확인한다.
3. B를 다시 시작한 뒤 제외 시간이 지난 상태에서 조회를 보낸다. 실제 조회의 연결 성공으로 B가 복귀하고 다시 교대한다. 조회가 없을 때 주기적으로 연결해 확인하지 않는다.
4. 선택 가능한 서버가 없거나 한 번의 우회도 실패하면 `502`를 반환한다. 연결에는 성공했으나 요청 송신을 시작한 뒤 실패한 경우에는 다른 서버가 같은 조회를 처리하지 않는다.

제외 시간은 개인 검증 기본값으로 먼저 **2초**를 권장한다. 동작 계약인 ‘제외 중 반복 연결 없음’과 ‘제외 후 실제 조회로 복귀’를 확인하되, 테스트는 정확히 2초 경계에서 성공하는지에 의존하지 않는다.

## 5. 느린 B의 영향 관찰

정상 A·B와 B만 느린 경우를 같은 요청 조건에서 비교한다. 조회와 제출의 지연·실패율을 함께 기록한다. B가 연결에 성공하고 제한 안에 응답하면 단순히 느리다는 이유로 제외되지 않는다. 이 실험 결과는 정상 라운드 로빈이나 종료 시 우회의 통과 여부와 분리하며, 향후 동시성 도입 또는 분배 정책 변경의 근거로 사용한다.

## 6. 설정 파일

`proxy_config_init()`은 파일이 없으면 내장 기본값(제출 `8001`, 조회 `8002`·`8003`)을 쓰고, 있으면 `submit` 한 줄과 `lookup` 한 줄 이상을 읽는다. 단위 테스트는 다음을 확인한다.

- 기본값에서 제출은 고정 1곳·1회 시도, 조회는 2곳·2회 시도이며 선택·결과 기록 함수와 그룹 상태가 연결된다.
- 주석·빈 줄·IPv6 대괄호 표기(`[::1]:9003`)를 허용하고 지정한 주소·포트를 그대로 확정한다.
- `submit` 누락·중복, `lookup` 누락, 알 수 없는 키, 잘못된 포트·주소, 토큰 초과, 8개 초과 `lookup`, 없는 파일은 실패한다. 실패한 호출은 직전 확정 설정을 바꾸지 않는다.
- 서버 실행 시 설정 오류는 수신 대기 전에 종료되고, 정상 파일은 그 주소로 실제 중계한다(E2E).

## 7. 모의 백엔드

[`tools/mock_backend.py`](../../../tools/mock_backend.py)는 세 백엔드가 같은 코드를 쓰고 `--id`만 다르게 주는 실행 도구다. 부하·장애 형태를 옵션으로 바꿔 같은 프록시를 반복 검증한다.

```sh
python3 tools/mock_backend.py --port 8001 --id submissions
python3 tools/mock_backend.py --port 8002 --id lookup-a
python3 tools/mock_backend.py --port 8003 --id lookup-b --delay-ms 300
./build/server 18080 config/routes.conf.example
```

| 목적 | 옵션 | 프록시에서 확인할 것 |
| --- | --- | --- |
| 조회 부하 단계 | `--delay-ms`, `--jitter-ms` | 느린 B가 제외되지 않고 200을 중계하며 지연만 늘어난다. |
| 백엔드 무응답 | `--hang-rate 1 --hang-ms 10000` | 최종 헤더 대기 제한 초과 시 `504 Gateway Timeout`. |
| 부분 응답 | `--body-bytes 100 --truncate-bytes 5` | 헤더·일부 본문 뒤 연결 종료, 새 오류 응답을 붙이지 않는다. |
| 백엔드 실패 응답 | `--fail-rate 1` | 정상 형식 `500`을 본문·상태 그대로 중계한다. |
| 큰·느린 본문 | `--body-bytes`, `--slow-body-ms` | 동반 본문 우선 중계와 본문 무진행 판정을 구분한다. |
| 분산·재시도 확인 | `GET /__stats` (백엔드 직접) | A·B가 실제로 받은 요청 수와 동시 처리 최대치를 본다. |

`/__stats`는 프록시를 거치지 않고 백엔드 포트에 직접 접속한다. 응답의 서버 식별자만으로는 "B를 건너뛰었다"와 "B에 연결했다가 실패했다"를 구분할 수 없으므로 이 카운터를 함께 본다.

## 8. 엣지 케이스: 잘못된 요청·크기 경계·백엔드 타임아웃

`docs/requirements/web-server.md`의 품질 체크리스트 중 잘못된 HTTP 요청, 매우 큰 본문·긴 URI, 백엔드 무응답/타임아웃을 현재 구현에서 확인한 결과다. 파서·본문 상한의 기준 정책은 바꾸지 않았으며, 기존 기준 문서인 [Iteration 2 테스트](../../iteration-2/Snoopykid/iteration-2-tests.md)를 그대로 따른다. 이 절은 이번 구현에서 관측한 동작을 기록한다.

실행 환경은 Linux이며, 일반 `build/server`와 `-fsanitize=address,undefined` 빌드에서 같은 검사를 수행했다. `make test` 19개와 `make verify`의 Iteration 1~4 회귀는 먼저 모두 통과했다. 이 절에서 확인한 34개 검사도 두 빌드에서 모두 통과했고 sanitizer 오류 로그는 없었다. 엣지 프로브에서는 누수 탐지를 끄고 실행했으며, 누수 검사는 `make test`의 ASAN 빌드가 담당한다.

재현: `python3 scripts/verify_edge_cases.py` 또는 `make verify-edge`. 이 검사는 약 22초가 걸리며 두 번의 5초 무입력 대기(408), 두 번의 3초 백엔드 대기(504), 2초 지연 백엔드 응답을 포함하므로 기본 `make verify`에는 넣지 않는다.

### 8.1 잘못된 HTTP 요청

| 입력 | 기대 | 실제 |
| --- | --- | --- |
| 헤더 도중 EOF (`Host`까지만 보내고 종료) | `400` | `400`, 즉시 |
| 헤더를 보낸 뒤 데이터 없이 연결 유지 | `408` | `408`, 약 5.1~5.5초 |
| 본문 1바이트만 보내고 연결 유지 (`Content-Length: 10`) | `408` | `408`, 약 5.1초 |
| 메서드에 금지 문자 포함 (`G@T`) | `400` | `400` |
| 소문자 메서드(`get`), `HEAD` | `501` | `501` |
| `HTTP/1.0`, `HTTP/2.0` | `505` | `505` |
| `HTTP/1.x`, `HTTP/1.1 junk` | `400` | `400` |
| 콜론 없는 헤더, 헤더 이름 공백, 값 제어문자, `Host :` | `400` | 모두 `400` |
| `Host` 누락 | `400` | `400` |
| 빈 연결(0바이트 후 종료) | 응답 없이 종료 | 이후 정상 요청 처리 |

헤더가 불완전한 채로 연결이 유지되면 전체 헤더 기한 7초 전에 약 5초에 `408`이 발생한다. `receive_socket_bytes()`가 호출별 `SO_RCVTIMEO` 5초 만료를 즉시 오류로 반환하기 때문이며, [Iteration 2 요구사항](../../iteration-2/Snoopykid/iteration-2-requirements.md)의 "아무 데이터도 오지 않으면 전체 기한 전 호출별 제한으로 끝날 수 있음"과 일치한다. 본문도 전체 15초 기한보다 5초 무입력 제한이 먼저 걸린다. 조각이 5초 안에 계속 도착하면 전체 기한이 적용된다.

### 8.2 매우 큰 요청 본문 / 매우 긴 URI

| 입력 | 실제 결과 |
| --- | --- |
| URI 8,002바이트 (`GET`) | `404`, 약 0ms |
| 쿼리 7,000바이트 (`GET /hello?...`) | `200 Hello` |
| URI 때문에 헤더 전체가 8,207바이트 | `431 Request Header Fields Too Large` |
| 본문 정확히 65,536바이트 (`POST /echo`) | `200`, 본문 그대로 echo |
| 본문 65,537바이트 선언 | `413 Content Too Large`, 본문 읽기 전 |
| 본문 10MiB 선언 | `413`, 약 0ms |
| `413` 응답 후 클라이언트가 1MiB 계속 전송 | `413` 수신, 서버 정상 유지. 클라이언트는 `BrokenPipeError` 가능 |
| 프록시 경로로 64KiB 본문 전달 | `201`, 백엔드가 `received: 65536` 확인 |

큰 본문은 `Content-Length`만 보고 `http_parse_request()`에서 할당 전에 `413`으로 거부한다. 10MiB 본문이 들어와도 10MiB를 `malloc`하지 않는다. `413` 응답 후 `handle_client()`가 최대 64KiB/1초만 폐기하고 연결을 닫으므로, 계속 보내는 클라이언트는 `BrokenPipe`를 볼 수 있다.

### 8.3 백엔드 무응답 / 타임아웃

| 조건 | 실제 결과 |
| --- | --- |
| 백엔드가 2초 뒤 응답 | `201`, 약 2.0초(3초 제한 안이므로 504 아님) |
| 백엔드가 연결만 받고 아무 응답 없음 | `504 Gateway Timeout`, 약 3.0초 |
| 백엔드가 `HTTP/1.1 200 OK\r\n`만 보내고 정지 | `504`, 약 3.0초(부분 수신해도 기한 갱신 안 함) |
| 백엔드가 헤더 + 본문 5바이트만 보내고 정지 | 클라이언트는 `200`과 5바이트를 받은 뒤 약 1.0초 후 연결 종료, 두 번째 응답 없음 |
| 본문을 300ms 간격으로 계속 보내 총 2.1초 소요 | `201`, 본문 2,000바이트 정상 완료 |
| 타임아웃 발생 후 조회 요청 | `200`, 정상 처리 |
| 반복 실패 후 FD 수 | 4 → 4, 누적 없음 |

프록시 관련 값은 최종 응답 헤더 대기 3초, 연결·요청 송신·본문 무진행 제한 1초다. [Iteration 4 요구사항](iteration-4-requirements.md)과 [Issue #17](https://github.com/chan95821/jungle-week-13-c-web-server/issues/17)의 "연결 제한 1초·백엔드 무응답 3초" 조건에 맞췄다. 순차 서버에서는 백엔드가 응답하지 않을 때 최대 3초 동안 다음 클라이언트 처리가 대기하며, 이 영향은 Iteration 5의 동시성 도입 뒤 다시 확인한다.

### 8.4 관측 요약

- 잘못된 요청은 시작 줄·헤더 문법·버전·Host 검증에서 `400`, `501`, `505`로 분리되고, 불완전 입력의 EOF와 시간 초과가 각각 `400`·`408`로 구분된다.
- 크기 상한은 헤더 8KiB, 본문 64KiB이며, 초과는 수신 전에 `431`·`413`으로 거부된다.
- 백엔드 무응답은 최종 응답 전 `504`, 응답 시작 후 본문 중단은 새 응답 없이 연결 종료로 드러난다.
- 정상·오류 경로를 반복한 뒤에도 FD가 누적되지 않고 다음 요청이 처리된다.
