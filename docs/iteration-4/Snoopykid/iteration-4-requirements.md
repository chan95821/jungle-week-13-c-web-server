# Iteration 4 개인 요구사항과 후속 경계

기록일: 2026-11-24. 사용자 계획 수정에 따른 개인 구현 기준이며 팀 채택 문서는 아니다.

## 현재 단계의 확정 범위

- Issue #4의 Reverse Proxy 필수 중계와 기존 정적·동적 기능을 유지한다.
- Issue #17의 POST /api/submissions → 제출 백엔드, GET /api/submission-status → 조회 A/B 중 한 곳을 구현한다. 요청 경로를 재작성하지 않는다.
- C/POSIX로 순차 처리한다. 백엔드 분산 자체가 병렬 처리를 제공하지 않으며 느린 한 요청은 다음 요청을 지연할 수 있다.
- 최종 응답 송신 시작 후 새 오류 응답을 덧붙이지 않는다.
- 요청별 상태·버퍼·FD 수명과 소유권을 명확히 한다. 변경 가능한 전역 상태와 I/O의 불필요한 결합을 피한다.
- 기존 C 서버를 테스트 백엔드로 재사용하되 프록시 코드와 테스트 백엔드 코드를 명확히 분리한다. Python은 검증 스크립트에만 사용한다.
- 합의한 함수 흐름 단위로 구현하고 main부터 실제 코드 순서대로 리뷰한다. 함수명·변수명은 역할과 데이터 의미가 드러나게 한다.

## Iteration 5에서 구현할 방향

- 여러 작업자가 각자 non-blocking 이벤트 루프로 여러 클라이언트·백엔드 연결을 관리한다. 연결별 작업자 생성 모델이 아니다.
- 외부 클라이언트 주소·포트는 하나다. 작업자별 외부 포트는 요구하지 않는다.
- 프로세스/스레드는 장애 격리·메모리·공유 상태·구현 및 검증 비용을 비교한 뒤 사용자가 선택한다.
- 연결 수락·분배 방식은 구현 전 선택받는다. 작업자 수, 이벤트 API, 조회 분배 상태의 작업자 간 공유 범위도 미결정이다.
- 백엔드 연결·읽기·쓰기를 기다리는 동안 다른 연결을 막지 않도록 한다. 느린 클라이언트의 버퍼 상한·역압력·타임아웃 정책을 먼저 선택받는다.
- 현재 blocking 본문 공급자 호출은 그대로 이벤트 루프에서 실행할 수 있다고 가정하지 않는다. 준비됨/대기 중/완료/실패 상태와 수명·취소 계약을 그 단계에서 설계한다.
- 동시 연결 10,000개는 검토 목표다. 처리량이나 지원 가능성을 보장하지 않는다.

## 아직 선택 전인 Iteration 4 사항

백엔드 주소 범위, 중계할 HTTP 및 헤더 범위, 타임아웃, 구체 자원 소유권·오류 정책은 이전 추천만으로 확정하지 않는다.

C 백엔드 재사용의 진입점·역할 설정·응답 계약·장애 재현 방법도 별도 흐름 설계에서 설명한다. Python 백엔드 추천은 사용자 선택으로 폐기했다. 조회 A/B는 동일 역할과 고정 상태, 서로 다른 식별자를 사용한다. 실제 저장·실시간 동기화·장애 자동 우회는 추가하지 않는다.

- Iteration 4의 작업자·이벤트 루프 구현, 로그인·세션·토큰·권한 관리, 캐싱, 여러 프록시 배치는 제외한다.
- 컴파일과 공식 기능·회귀 검증은 별도 보고한다. 구현 종료 후 검증 후보와 통과 기준을 제시하고 범위를 확정받는다.
- 부하·성능 실험은 요청률·본문 크기·백엔드 지연·CPU·메모리·FD 조건과 측정 지표를 제시하고 명시적 허락 후 실행한다.
- 이 문서 수정은 코드 구현·검증·성능 측정 실행을 뜻하지 않는다.

## Iteration 4 확정 추가 및 분배 한계 (2026-11-24)

- 실행 설정은 ./build/server <port> <proxy.conf> 파일 방식이다. public 정적 루트는 유지한다.
- GET /api/hello는 조회 A/B로 분배하며 원래 경로·쿼리를 보존한다.
- Iteration 4는 Round-Robin을 사용한다. 선택 시 순번을 넘기고 실패 시 다른 백엔드로 자동 재전송하지 않는 추천안을 기준으로 한다. 제출 POST도 자동 재시도하지 않는다.
- Iteration 5의 진행 중 요청 수 기준 선택과 동률 시 Round-Robin은 검토 후보이며 최종 채택은 아니다. 응답 시간 기반 자동 전환도 현재 확정 범위가 아니다.
- 반례: 조회 A가 매우 무거운 요청 1개를 처리하고 B가 가벼운 요청 2개를 처리하면 요청 수만 비교하는 방식은 A를 선택할 수 있다. 진행 중 요청 수는 실제 CPU·메모리·요청 비용을 보장하지 않는다.
- 후속 검토 후보는 응답 시간·미완료 요청의 경과 시간·백엔드 제공 부하·알려진 요청 비용과 용량 가중치, 백엔드별 동시 요청/대기열 상한이다. 관측 지연·공유 상태·재확인·오탐·구현 및 검증 비용을 비교하고 선택받는다. 타임아웃만으로 백엔드 연산 중단을 보장하지 않는다.
- 기본 검증 후보에 무거운 요청 1개 대 가벼운 요청 여러 개의 분배 반례를 등록한다. Iteration 5 검토 항목이며 이번에 계측·장애 자동 우회·부하 실험을 구현하거나 실행하지 않는다.

## 연결·중계 범위 추가 확정 (2026-11-24)

- 백엔드는 숫자 IPv4와 포트로 지정한다. 호스트명/DNS는 후속 검토다.
- 요청마다 백엔드 연결 하나를 생성·정리한다. 연결 재사용은 후속 검토이며 Iteration 5 동시성과 별개 정책이다.
- 기존 64KiB 상한 안에서 요청 본문을 수신 완료한 뒤 백엔드로 전달한다. 수신 중 중계는 후속 검토다.
- 백엔드 응답은 HTTP/1.1만 지원한다. Content-Length·chunked·연결 종료 본문을 지원하는 방향이다. HTTP/1.0 지원은 이번에 추가하지 않으며 후속 항목도 자동 도입하지 않는다.
- 전달 대상 헤더를 보존하고 hop-by-hop 헤더를 제거한다. Host는 백엔드 주소로 변경하고 Via를 추가한다. 원래 Host 보존은 후속 검토다.
- 임시 16KiB 버퍼로 응답을 스트리밍하며 전체 본문을 할당하지 않는다. 전체 저장은 후속 검토다.
- 타임아웃·오류 매핑·구체 FD 소유권의 이전 추천은 위 6개 선택의 일괄 승인으로 간주하지 않는다. 실제 소켓 중계 전에 별도 확정한다.

## 첫 구현 흐름: 설정과 목적지 선택

- 설정 파일은 submission, query-a, query-b 각 역할과 IPv4:port를 공백으로 구분해 한 줄씩 지정한다. 빈 줄과 # 주석을 허용한다. 세 역할은 정확히 한 번씩 필요하며 알 수 없는 역할·중복·잘못된 주소/포트·추가 토큰은 거절한다.
- 예: submission 127.0.0.1:8001 / query-a 127.0.0.1:8002 / query-b 127.0.0.1:8003 (각각 별도 줄).
- 경로·메서드 계약은 고정하고 백엔드 주소를 설정한다. 범용 라우팅 DSL은 추가하지 않는다.
- 조회 두 경로는 같은 A/B 풀과 순번을 사용한다. POST 제출과 로컬 경로·잘못된 메서드 판별은 조회 순번을 소비하지 않는다.
- 설정 로더는 임시 구조에서 모두 검증한 뒤 호출자 출력에 복사한다. 선택 함수는 호출자가 제공한 순번만 변경하며 전역 상태·소켓 I/O·FD를 사용하지 않는다.
- 이 흐름은 모듈과 단위 테스트의 컴파일까지 진행한다. main의 실행 인자와 실제 중계 통합은 남은 소유권·오류 정책 확정 후 진행한다.

## 중계 구현 전 확정 및 흐름 (2026-11-24)

- 사용자 승인: 연결 전체 1초, 요청 전달 전체 5초, 응답 헤더 전체 1초, 본문 무진행 5초 및 본문 전체 15초. 실험 전 임시 상수이며 기존 클라이언트 수신 정책은 유지한다.
- 연결 거절·잘못된 백엔드 응답 502, 백엔드 시간 초과 504, 내부 할당 실패 500. 최종 응답 송신 시도 뒤에는 새 오류 응답을 붙이지 않는다.
- main이 설정·조회 순번과 클라이언트 FD, handle_client가 요청 메모리를 소유한다. 프록시 응답 상태가 백엔드 FD·응답 헤더·16KiB 스트림 버퍼를 소유하고 provider cleanup에서 정리한다. 준비 실패 시에는 준비 함수가 정리한다.
- 실제 흐름: main 설정 읽기 → handle_client 헤더/본문 수신 → 목적지 선택 → proxy_prepare_response 연결/요청 전달/응답 헤더 검증 → send_prepared_response 상태·헤더 및 provider 본문 전송 → provider cleanup → 클라이언트 종료.
- 요청/응답의 일반 헤더는 포인터+길이로 순회하며 중복 필드를 무조건 합치지 않는다. Connection 및 그 지명 헤더, Keep-Alive/Proxy-Connection/TE/Transfer-Encoding/Upgrade 등의 연결별 필드는 전달하지 않고 프레이밍을 재생성한다. Expect는 프록시에서 처리했으므로 백엔드로 재전달하지 않는다.
- 백엔드 HTTP/1.0·101 Upgrade와 잘못된 프레이밍은 502다. 최종 응답 전의 일반 1xx는 최종 응답 헤더 기한·출력 헤더 공간 안에서 보관해 최종 헤더 검증 후 전달한다. 프록시가 처리한 100은 중복 전달하지 않는다.
- 백엔드 헤더와 chunk metadata의 저장 한도는 기존 요청 헤더 상한 8KiB를 재사용한다. 전체 응답 본문은 저장하지 않는다. 고정 길이는 조기 EOF를 실패 처리하고, chunked·연결 종료 본문은 클라이언트에 chunked로 전송해 오류 시 정상 종료 청크를 생략한다.
- 테스트 백엔드는 tests/backends 아래 별도 main과 역할·장애 응답을 두고 기존 C 리스너/파서/송수신 코드를 링크해 재사용한다. Python은 프로세스·요청 검증만 한다.
- 사용자가 설정 예시를 build/proxy.conf.example로 이동했다. 빌드/clean은 이 파일을 생성·덮어쓰기·삭제하지 않는다. 설정 문법은 문서에 보존하며 tests는 임시 설정 파일을 작성한다.
