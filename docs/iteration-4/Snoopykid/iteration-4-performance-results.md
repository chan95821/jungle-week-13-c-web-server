# Iteration 4 보완 결과와 성능 비교

2026-11-25 승인된 보완 및 검증 기록을 종합했다. 비교 대상은 보완 전 f32e17d와 보완 후 측정 당시의 격리 스냅샷이다. 원시 자료의 baseline/current는 각각 이 두 대상을 뜻한다. 측정 당시 보완 코드는 미커밋 상태였으며, 측정 대상 소스와 바이너리는 [manifest](performance/manifest.json)의 SHA256으로 식별한다. 이후 게시된 커밋과 측정 시점의 상태를 혼동하지 않도록 아래 과거 실행 기록은 보존한다.

## 먼저 읽을 내용

이번 보완의 성과는 **책임이 분리된 코드, 짧고 명확해진 버퍼 수명, 하나로 모인 라우팅, 더 구체적인 오류·자원 검증**이다. 실행 속도는 구간에 따라 좋아지거나 나빠졌고, 포화 조회 처리량의 중앙값은 1.55% 낮아졌다. 구조 개선을 곧바로 성능 향상으로 해석하지 않는다.

| 평가 관점 | 보완 결과 | 근거와 해석 범위 |
| --- | --- | --- |
| 구조·가독성 | 연결·헤더·본문 책임 분리, 로컬/프록시 라우팅 일원화 | 실제 모듈과 단일 라우팅 진입점으로 확인. 유지보수 시간 단축을 수치로 측정한 것은 아니다. |
| 메모리 수명 | 스트림에 남기는 고정 배열을 줄이고 필요한 데이터만 보존·해제 | 코드상 용량·소유권 개선이다. 전체 연결 메모리나 RSS가 같은 비율로 줄었다는 뜻은 아니다. |
| 오류·검증 | 보호 헤더 조기 거절, 할당 실패·트레일러·FD 회수·라우팅 우선순위 검증 강화 | 개별 실행 기록의 단위 8개·E2E 6개·엣지 40개 통과. E2E 6개 안에 엣지 스크립트가 포함된다. |
| 정상 부하 처리 | 모든 고정 요청률 10~400건/초 달성 | 48회 측정에서 실패·5xx·예정 요청 누락 0건. 정상 1KiB 응답 조건이다. |
| 포화 처리 성능 | 조회 3,920.8 → 3,859.9건/초, 제출 p95 4.913 → 4.485ms | 조회 처리량은 소폭 낮아지고 제출 꼬리 지연은 줄었다. 짧은 3회 측정이므로 지속적인 변화와 원인은 미확정이다. |

## 실제로 개선한 구조와 책임

### 프록시 처리 흐름을 책임별로 분리

기존에는 proxy_transfer.c에 연결·요청 전달·응답 헤더·본문 처리가 모여 있었다. 보완 후에는 상위 함수가 전체 흐름과 소유권을 조율하고, 하위 모듈이 각 단계의 일을 수행한다.

| 파일 | 현재 책임 | 코드를 읽거나 바꿀 때 얻는 점 |
| --- | --- | --- |
| src/proxy_transfer.c | 응답 상태 생성, 준비 단계 조율, 소유권 이전·정리 | 연결부터 정리까지 상위 흐름을 따라갈 수 있다. |
| src/proxy_io.c | 백엔드 연결, 수신 버퍼, 전체/무진행 기한 | 대기·부분 수신·타임아웃 관련 코드를 모아서 검토한다. |
| src/proxy_headers.c | 요청 전달 헤더, 응답 파싱·재구성, Connection 정보 보존 | HTTP 헤더 정책을 본문 전송과 구분해 검토한다. |
| src/proxy_body.c | 고정 길이/chunked/EOF 본문 공급, 출력 헤더 회수, 트레일러 검사 | 본문 경계와 송신 후 정리 동작을 한 책임 안에서 확인한다. |
| src/proxy_internal.h | 내부 상태와 모듈 간 함수 계약 | 모듈이 공유하는 상태·수명을 명시한다. |
| src/router.c / router.h | 로컬·프록시 규칙과 http_select_route 진입점 | 경로·메서드·목적지 역할을 한 규칙표에서 확인한다. |

실제 요청 흐름은 다음과 같다.

~~~text
main()
 → handle_client()
    → http_parse_request()       요청 구문·길이 검사
    → http_select_route()        로컬/프록시 경로·메서드 선택
    → proxy_validate_request()   성공한 프록시 경로의 보호 헤더 검사
    → 필요한 본문 수신·100 Continue 처리
    → 로컬 처리 또는 백엔드 선택·proxy_prepare_response()
       → connect_backend()
       → forward_request_to_backend()
       → prepare_backend_response_headers()
    → send_prepared_response()
       → read_backend_body_chunk() 반복
       → cleanup_backend_response()
 → 클라이언트 FD 정리
~~~

흐름의 각 함수는 프로젝트 함수이며, 내부에서 socket/connect/recv/send/close 등의 POSIX API를 호출한다. 이 분리가 여러 연결을 병렬 처리하는 이벤트 루프를 의미하지는 않는다. 현재 순차 처리와 I/O 계약은 유지한다.

### 버퍼를 사용하는 단계에 맞춰 수명 정리

| 항목 | 보완 전 | 보완 후 |
| --- | --- | --- |
| 스트림 내부 고정 배열 합 | 49,408바이트(48.25KiB) | 본문 스트림 버퍼 16,384바이트(16KiB) |
| 원본 헤더·재구성 작업 공간 | 스트림 상태에 보관 | 헤더 준비 단계의 지역 작업 공간. 해당 배열 합 24,832바이트(24.25KiB) |
| 출력 헤더 | 고정 공간을 스트림에 보관 | 완성된 길이만 할당하고 헤더 송신 후 첫 본문 공급 시 회수 |
| 트레일러 검사에 필요한 Connection 정보 | 원본 헤더를 참조 | 필요한 필드만 복사해 본문 처리 중에도 유효한 수명 보장 |
| 트레일러 | 고정 공간 보관 | 유효한 비어 있지 않은 값이 있을 때 필요한 길이만 할당 |
| 본문 없음·송신 실패 | 기존 정리 경로 | 본문 공급이 한 번도 호출되지 않아도 cleanup이 확보 자원을 회수하도록 검증 |

핵심은 **모든 준비용 공간을 본문 전송이 끝날 때까지 들고 있지 않는 것**이다. 지역 배열·메타데이터·동적 헤더·트레일러 공간은 여전히 존재한다. 이 표로 전체 메모리 감소율을 계산할 수 없고, 동적 할당·복사 비용과 작업자 스택 예산도 고려해야 한다. 뒤의 RSS 측정은 이 코드상 용량 설명과 별개다.

### 라우팅 판별을 한 곳으로 통합

- 로컬 8개·프록시 3개 규칙을 router.c의 routes[]에 모았다. http_select_route가 경로·메서드 선택의 단일 진입점이다.
- proxy.c의 중복 경로/메서드 if/else와 proxy_match_request, 기존 http_select_handler는 제거했다. proxy_validate_request는 보호 헤더 검사만 담당한다.
- 실제 백엔드 주소와 Round-Robin 순번은 기존 proxy_config/proxy_selection_state에 남겼다. 라우팅만으로 백엔드 순번이 바뀌지 않는다.
- 파서 오류가 먼저이고, 라우팅 오류 404/405/501, 정상 프록시의 보호 헤더 검사, 본문·100 Continue, 백엔드 연결 순서를 유지한다. 새 콜백·공유 상태·할당·I/O는 도입하지 않았다.

## 성능 결과 요약

- 측정 48회 완료. 정상 검증된 응답 165,929건, 실패 0건, HTTP 5xx 0건. 워밍업 실패 0건.
- 포화 조회 처리량 중앙값: 보완 전 3,920.8 → 보완 후 3,859.9 req/s (-1.55%).
- 3회 최소~최대 범위가 겹친다. 이 결과만으로 안정적인 개선/저하를 단정하지 않는다.
- 고정 요청률의 예정 건수 미달 사례: 0개. 측정 전후 FD 수 차이: 0개.

## 측정 조건

- Ryzen 7 4800H(8코어/16논리 CPU), Ubuntu WSL2, WSL 메모리 약 7.5GiB. 호스트 16GB는 사용자 제공 정보와 구분한다.
- 공통 C 백엔드 제출1/조회2, 각 응답 1024바이트·인위 지연0. 제출은 1024바이트 바이너리 echo, 조회는 동일한 바이트 패턴이다. 기존 C 백엔드의 benchmark 모드를 두 후보에 똑같이 사용했다.
- C11 -Wall -Wextra -Werror -O2, sanitizer 없는 측정 바이너리. C 부하 생성기, Python은 실행/자원 관찰/집계만 담당한다.
- 요청마다 새 TCP 연결, 클라이언트 요청 완료 후 SHUT_WR, 응답은 EOF까지 수신. 전체 요청 제한시간5초. 상태/Content-Length/1024바이트 내용/백엔드ID가 맞아야 성공이다.
- 제출2req/s(최대 동시2), 조회10/25/50/100/200/400req/s(최대 동시16). S_MAX 조회는 동시16 closed-loop이며 제출2req/s를 병행한다.
- 각 조건 워밍업5초 후3회. S1 측정60초, S2~S6 각8초, S_MAX 5초. 직접 백엔드 기준선은 S1/S5이며 조회 A/B를 클라이언트에서 교대로 선택한다.
- 후보당 프록시는 매 회 새로 시작한다. 3개 백엔드는 공통 세션에서 유지한다. 단계별 후보 실행 순서는 반복1/3 보완전→후, 반복2 보완후→전이다.
- 지연은 클라이언트 socket 생성 직전부터 응답 EOF·바이트 검증·close까지다. 단위ms, 성공 응답의 nearest-rank p50/p95만 집계한다. 표는 반복별 값의 중앙값(최소–최대)이며 모든 응답을 합친 전역 p95가 아니다.
- 처리량은 성공 건수/부하 생성기의 실제 경과시간(마지막 요청 정리 포함)이다. 고정률 도구는 동시수 상한이 있어 무한 큐를 만들지 않는다. 예정 건수 미달과 실패를 별도로 기록한다.

## 성능 수치를 읽는 방법

| 지표 | 쉬운 설명 | 이 실험에서 주의할 점 |
| --- | --- | --- |
| req/s(건/초) | 1초에 완전히 검증된 응답을 몇 건 완료했는가 | 요청을 보낸 수가 아닌 성공 완료 건수다. 마지막 요청 정리까지 포함한 실제 경과시간으로 나눈다. |
| p50(ms) | 한 실행의 성공 응답 중 절반이 이 시간 안에 끝났다 | 보통의 응답 시간에 가깝지만 평균은 아니다. 1ms는 0.001초다. |
| p95(ms) | 한 실행의 성공 응답 중 95% 이상이 이 시간 안에 끝났다 | 나머지 약 5%는 더 느릴 수 있으며 최대 지연이 아니다. 표는 실행별 p95 세 개의 중앙값이다. |
| CPU 초 | 프로세스가 실제 CPU에서 일한 시간의 합 | 벽시계 경과시간이나 요청 하나의 처리 시간이 아니다. |
| CPU % | 관찰 시간 중 논리 CPU 한 개를 얼마나 사용했는가 | 100%는 논리 CPU 1개 기준이며 노트북 전체 CPU 100%가 아니다. |
| RSS(KiB) | 관찰 시점에 프로세스가 물리 메모리에 올려 둔 페이지 용량 | 1KiB는 1,024바이트. 요청 버퍼·힙 할당량 자체가 아니며 순간 피크를 놓칠 수 있다. |
| FD 수 | 열려 있는 파일·소켓 등의 자원 수 | 전후 수가 같다는 것은 관찰한 실행에서 누적이 없었다는 뜻이며 모든 경로의 누수 부재 증명은 아니다. |

예를 들어 보완 후 S1의 **조회 p95 1.591ms**는 각 60초 실행에서 구한 p95 세 값 중 가운데 값이다. 해당 실행의 조회 성공 응답은 95% 이상이 약 0.001591초 안에 끝났다. 이 시간에는 클라이언트 연결 시작부터 프록시·백엔드 통신, EOF 수신·본문 검증·close까지 들어간다.

### 얼마 동안, 얼마나 많은 요청을 보냈는가

각 측정 회차 전에 5초 워밍업하고 아래 시간을 측정했다. 보완 전·후 각각 3회 실행했으며 직접 접속 기준 S1/S5도 각 3회 포함해 총 48회다. 워밍업 결과는 측정 결과와 분리했다.

S_MAX에서는 **보완 전 약 5초 동안 조회 19,397~19,884건**, **보완 후 18,867~19,777건**을 완료했다. 실제 경과시간은 마지막 요청 정리를 포함해 약 5.004~5.005초다. 이를 초당 완료 건수로 환산한 중앙값이 각각 **3,920.8건/초와 3,859.9건/초**다. 5초를 넘는 지속 처리 능력이나 장시간 운영 용량을 보장하지 않는다.

### 변화의 의미

- **포화 조회 처리량:** 중앙값 기준 초당 약 61건(1.55%) 낮아졌다. 첫 반복은 보완 후가 더 높았고 나머지 두 반복은 낮았으며, 최소~최대 범위도 겹친다. 실제 저하 가능성을 배제하지 않되 지속적인 차이라고 확정하지 않는다.
- **포화 조회 p95:** 4.569 → 4.651ms로 약 0.082ms 늘었다. 반면 제출 p95는 4.913 → 4.485ms로 약 0.428ms 줄었다. 조회와 제출의 변화 방향이 같지 않다.
- **S5:** 조회 p95는 1.362 → 1.344ms로 소폭 줄었지만 제출 p95는 1.222 → 1.409ms로 늘었다. 제출은 회차당 16건뿐이라 p95가 소수의 느린 응답에 민감하다.
- **관찰과 원인 구분:** 여러 기능·구조 보완을 함께 비교했다. 할당·복사·검사·스케줄링 중 어떤 요소가 차이를 만들었는지는 이 측정으로 분리하지 않았다.

## S_MAX 자원 사용

## 한계 및 해석

- 이 비교는 f32e17d 이후 HTTP/1.0·보호 헤더·헤더 정책·모듈/메모리·라우팅 보완 전체 묶음의 효과다. 메모리 리팩토링만의 인과 효과로 분리하지 않았다.
- 기존 핸드오프는 다른 Linux/Go 백엔드·부하 도구였다. 이번 C/WSL 결과로 기존 4,937req/s 유지 여부를 판정하거나 외부 후보 순위를 다시 매기지 않는다.
- 같은 노트북에서 프록시·백엔드·부하 생성기가 CPU/메모리를 경쟁한다. 부하 생성기 병목을 완전히 배제하지 못했다. CPU 고정·네트워크 sysctl·FD 한도 변경은 하지 않았다.
- 정상 1KiB 응답 조건의 결과다. 느린/장애 백엔드·큰 본문·1만 연결·장시간 메모리 증가는 측정하지 않았다. 순차 처리의 head-of-line blocking이 해결된 것은 아니다.
- S2~S6의 제출은 반복당 약16건, S_MAX는 약10건이므로 제출 p95 표본이 작다. 관측 변동을 포함하며 개선 보장으로 확대하지 않는다.
- 측정 당시 최적화·정책 변경·추가 측정을 자동 적용하지 않았고, 측정 작업 자체에서 머지·커밋·푸시를 하지 않았다. 이후 게시 상태와 구분하는 과거 실행 기록이다. 이번 문서 편집에서도 소스 변경·추가 측정은 하지 않았다.
