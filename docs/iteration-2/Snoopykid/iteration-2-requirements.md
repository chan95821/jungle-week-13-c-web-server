현재 상태: 사용자 선택 최소 범위를 구현하고 컴파일했다. 공식 검증·성능 측정은 미실행이다. 아래 초안·결정 기록의 미구현/선택 대기는 각 기록 당시 상태이며, 최신 범위는 「Iteration 2 최소 범위 확정과 구현 순서」와 PLAN.md의 구현 결과를 따른다.

기록 경로의 Snoopykid는 현재 gh 인증 계정 조회 결과다. 현재 브랜치는 feat/iteration-2-YYJ다. 폴더명은 기록의 구분자이며 팀 브랜치 변경·전환은 수행하지 않았다.

- HTTP/1.1 요청 라인·헤더·본문을 해석하고 GET /hello 응답, POST /echo 본문 반환을 구현하는 것이 목표다.

## 현재 코드에서 확인한 사실

- src/server.c의 recv_until_header_end는 CRLFCRLF를 찾아도 out_len에 수신 전체 길이 total을 넣는다. 헤더 종료 위치는 반환하지 않는다.
- 한 recv에 본문 일부가 동반될 수 있다. 현재 버퍼는 이미 받은 본문을 담을 수 있지만 handle_client는 이를 해석·보존해서 처리하지 않고 고정 응답을 보낸다.
- tests/unit/test_recv_header.c의 test_with_trailing_body는 헤더와 hello가 동반된 전체 수신 길이를 기대한다. 기존 함수의 길이 의미를 바꾸면 이 계약과 사용처를 함께 검토해야 한다.
- 연결 FD는 main에서 닫는다. 수신·응답 조율 함수는 FD를 빌려 사용한다. 요청 구조·버퍼의 소유권과 API는 아직 선택 전이다.
- 현재 팀 바이너리는 ./server, 정상 고정 응답은 text/plain 및 Hello 5바이트다. 루트의 이전 개인 server.c·webserver는 기반 구현으로 사용하지 않는다.

## 표준 근거와 선택 가능한 범위

- [RFC 9112 §3.2](https://www.rfc-editor.org/rfc/rfc9112.html#section-3.2): HTTP/1.1에서 Host 누락·복수 필드·잘못된 값은 400 대상이다. 필수 규칙을 선택 사항으로 취급하지 않는다.
- [RFC 9112 §6.3](https://www.rfc-editor.org/rfc/rfc9112.html#section-6.3): 요청 프레이밍은 메서드와 독립적이다. 유효한 Content-Length 및 Transfer-Encoding에 따라 본문 경계를 판단한다.
- 사용자는 이번 단계에서 Content-Length 방식만 지원하는 학습 범위를 선택했다. Transfer-Encoding은 조용히 무시하지 않고 명시적으로 거부·종료하며, 완전한 HTTP/1.1 프레이밍 구현이라고 표현하지 않는다. chunked는 최종 소스 구현·검증 완료 시 재검토한다. 거부 상태 코드와 충돌 처리 세부 정책은 별도 검토한다.
- [RFC 9110 §10.1.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.1.1): Expect: 100-continue와 본문이 있는 요청은 본문을 기다리기 전에 헤더로 결정 가능한 최종 응답 또는 100 Continue를 보내야 한다. 구체적인 지원·거부 정책은 선택 전이다.
- 헤더 이름·용도는 [IANA HTTP 필드 등록부](https://www.iana.org/assignments/http-fields/)와 각 규격에 근거한다. 무관한 헤더 전체의 기능을 구현하는 것이 2단계 목표는 아니다.

| 헤더 | 검토 이유 | 결정 상태 |
|---|---|---|
| Host | HTTP/1.1 대상·필수 검증 | 표준 필수 규칙을 준수하며 파서 세부 범위 검토 필요 |
| Content-Length | 본문 바이트 길이·중복·오버플로우 | 세부 검증 정책 검토 필요 |
| Transfer-Encoding | 프레이밍 충돌 및 chunked | 이번 단계는 거부·종료. chunked는 최종 구현·검증 완료 후 재검토 |
| Connection | 현재 단계의 응답 후 종료 정책 | close 우선이라는 Issue 범위 내 세부 동작 검토 필요 |
| Content-Type | echo 응답 타입·원시 본문 취급 | /echo 응답은 application/octet-stream 고정. 요청 타입 반영 제외 |
| Content-Encoding | 압축된 바이트를 해석·반영할지 | 압축 해제는 이번 범위 제외. 수신 본문은 바이트 그대로 반환 |
| Expect | 본문 전송을 기다리는 클라이언트와의 순서 | 정상 요청에 필요한 100 Continue 지원으로 확정 |
| Accept, Accept-Encoding | 콘텐츠 협상·응답 압축 | 별도 기능 선택 전 |
| Authorization, Cookie | 인증·세션 | 이번 목표에 자동 추가하지 않음 |
| Range, 조건부 요청 필드 | 부분 응답·캐시 | 이후 기능과 함께 별도 검토 |

## 확정 결정 기록

| 항목 | 사용자 선택 | 이유·제한 |
|---|---|---|
| 본문 프레이밍 | Content-Length만 지원. Transfer-Encoding 검출 시 명시적 거부·종료 | 우선 길이 기반 최소 구현에 집중. chunked는 최종 소스 구현·검증 완료 시 검토 항목으로 유지 |

- 이후 선택 필요: 잘못된 경로·메서드·버전별 상태 코드, URI·헤더 개수 상한, 헤더 표현과 파싱 API, 지원 HTTP 버전·request-target 형태, Expect 정책, 읽지 않은 추가 데이터가 있는 연결의 종료 방식과 오류 검사 우선순위 등 남은 세부 규칙.

## 회귀 검증과 구분할 내용

- scripts/verify_iter1.py는 일부 정상 생존·재시작 확인 요청에 Host가 없다. 표준 Host 검증 이후 이 요청을 성공 사례로 유지하면 모순이다. 정상 사례에는 유효한 Host를 넣고, 누락 입력은 400 반례로 분리하는 방향을 검토한다. 아직 수정·실행하지 않았다.
- 프레이밍만 검사하는 저수준 단위 테스트에는 의미상 불완전한 요청이 있을 수 있다. 이를 전체 HTTP 요청의 유효성 테스트와 혼동하지 않으며 저수준 테스트를 무조건 삭제하지 않는다.
- 사용자는 GET /와 GET /hello 모두 text/plain, 줄바꿈 없는 Hello 5바이트로 응답해 루트 경로를 보존하기로 결정했다. 두 경로 모두 새 파서로 검증한다. 회귀 테스트 통과를 위해 Host 누락 등 잘못된 요청을 허용하지 않는다.

## 사용자 확정: 제한적 연결 종료와 Expect (2026-11-21)

이 절은 앞선 연결 종료·Expect 미결정 기록을 대체한다. 소스·테스트 코드는 아직 변경하지 않았고 공식 검증·성능 측정은 실행하지 않았다.

- 최종 응답을 정상 송신한 개별 연결은 쓰기 방향을 shutdown(SHUT_WR)한 뒤, 남은 데이터를 최대 1초 또는 64KiB 중 먼저 도달한 한도까지만 읽어 버리고 close한다. 추가 데이터를 현재 본문에 합치거나 다음 요청으로 처리하지 않는다.
- 1초와 64KiB는 임시 프로젝트 정책값이다. 1초는 폐기 단계 전체의 기한이며, 조각 도착 때마다 새 1초를 부여하지 않는다. 보관 없이 제한적으로 폐기하므로 거부 응답 전에 큰 본문 전체를 먼저 수신하는 동작이 아니다.
- 순차 처리에서는 폐기 대기 동안 다음 연결 처리가 지연될 수 있고, 제한 도달 후 close는 TCP reset 및 응답 유실 가능성을 완전히 없애지 못한다. 이는 정책상의 비용·한계이며 실측 성능 결과가 아니다.
- SIGINT/SIGTERM에 의한 서버 종료 중에는 폐기 완료나 진행 중 응답 완료를 기다리지 않고 일반 실행 흐름에서 자원을 정리한다. 개별 연결의 정상 종료 정책과 서버 셧다운 정책을 구분한다.
- 정상 Expect: 100-continue 요청은 요청 라인·헤더·길이·상한 등을 먼저 검사하고, 본문을 더 받아야 할 때 100 Continue를 보낸 뒤 수신한다. 헤더만으로 거부가 가능하면 413 등 최종 오류를 바로 보내고 100을 먼저 보내지 않는다.
- 이미 본문 전체가 수신됐으면 불필요한 중간 응답을 생략한다. 지원하지 않는 Expect 값 등 나머지 구문·거부 세부 규칙은 파서 정책 검토에서 확정한다.
- 100 Continue는 최종 200/오류 응답과 별개의 중간 응답이며 자체 본문을 갖지 않는다.
## Iteration 2 최소 범위 확정과 구현 순서 (2026-11-21)

사용자는 기본 요청 해석·본문 경계·메모리 안전 규칙, 정상 입력 처리 및 명시적 미지원 거절을 이번 단계에 포함하기로 결정했다. 광범위한 조합·장애·회귀 검증은 Iteration 6에서 확대한다. 기본적인 1단계 회귀와 2단계 성공·실패 검증 자체를 6단계로 모두 미루는 뜻은 아니다.

- HTTP/1.1 및 origin-form만 지원하는 제한 구현이다. 구문이 맞는 범위 밖 HTTP 버전은 505, absolute-form 등 미지원 요청 대상 형태는 501로 명시적 거부한다. 잘못된 구문은 400이다. 완전한 HTTP/1.1 지원으로 표현하지 않는다.
- 라우팅은 첫 물음표 앞의 원래 경로를 기준으로 한다. 퍼센트 이스케이프는 두 자리 16진 구문을 검사하되 디코딩하지 않고, 경로를 임의 정규화하지 않는다. fragment·공백·잘못된 제어문자·잘못된 퍼센트 구문을 정상 URI로 수용하지 않는다.
- 요청 필드는 원본 헤더의 포인터+길이를 빌려 참조한다. 연결 처리 함수의 헤더 버퍼는 응답 처리까지 유지하며, 파서는 입력을 NUL 구분 문자열로 바꾸지 않는다. 본문은 앞서 선택한 별도 할당·수명 규칙을 따른다.
- 길이 정보가 없으면 프레이밍상 본문 길이 0이며 POST /echo도 200·application/octet-stream·Content-Length: 0으로 응답한다. 뒤에 도착한 데이터를 본문으로 추측하지 않는다. 명시적 길이의 부족한 EOF·타임아웃은 성공 처리하지 않는다.
- 헤더 이름 대소문자 무시, 값 양끝 SP/HTAB 제거, 필드 이름·콜론 앞 공백·obs-fold·NUL·잘못된 제어문자 거절, 유효한 미지원 일반 헤더 건너뛰기, 유효한 단일 Host 검증을 포함한다.
- 알려지지 않은 경로 404, 지원 메서드 GET/POST와 경로의 불일치는 405 및 Allow, 다른 미구현 메서드 501, 지원하지 않는 Expect는 417로 거부한다.
- Content-Length/Transfer-Encoding 충돌·잘못된 전송 프레이밍은 400, 구문상 유효한 최종 chunked 프레이밍은 이번 미지원 범위이므로 501로 거부한다. 별도 필드 개수·더 작은 URI 상한을 자동 추가하지 않는다.

### 탑다운 함수 흐름

main: 포트·시그널 준비 → listening FD 생성 → 연결 수락 시각 기록 → handle_client → 연결 FD 닫기 → 다음 연결 또는 리스너 정리.

handle_client: 연결별 헤더·요청·본문 소유권 준비 → 헤더 수신(총 수신량과 헤더 끝 위치 분리) → 순수 파싱·프레이밍 검증 → 경로·메서드 검사 → 필요한 경우 100 Continue → 검증된 크기 한 번 할당 및 이미 받은 본문 보존 → 부족분만 수신 → 최종 응답 → 제한적 수신 폐기 → 본문 한 번 free. FD 최종 close는 main 소유다.

순수 HTTP 파싱·경로 판정은 소켓 I/O와 분리한다. 기존 저수준 recv_until_header_end·send_all 테스트 계약은 유지하고, 새 처리 경로에서는 종료 표시와 수신 기한을 전달한다. 시스템 함수(socket, recv, malloc 등)와 직접 만든 파서·조율 함수를 설명에서 구분한다.

### 지금과 Iteration 6의 검증 구분

- 지금 기본 후보: 요청 라인·Host·길이·중복/충돌·유효/잘못된 URI의 각 성공/실패, 빈/바이너리/분할/동반 본문, 8KiB·64KiB 경계, 기본 경로·오류·100 Continue, 정한 기한·연결 정리와 1단계 기본 회귀.
- 6단계 확대: 대규모 분할·중복·구문 조합 및 퍼징, 여러 자원 실패 시점의 오류 주입, 신호·I/O 경합·반복 장애·장시간 자원 회귀, 클라이언트 호환 조합. 성능·부하 측정은 6단계라도 별도 지표·조건 검토와 명시적 허락이 필요하다.
- 구현 후 컴파일은 확인하되, 공식 테스트 실행은 범위 검토·확정 전에는 하지 않는다.

### 구현 완료 후 같은 작업에서 이어서 할 설명

사용자 요청: main()에서 시작해 실제 코드 흐름대로, 대화에서 함께 정한 정책과 이유가 연결되도록 설명한다. 연결 수락·파싱·본문 소유권·수신 기한·100 Continue·최종 응답·폐기·free/close를 코드 위치와 연결하고, 컴파일 확인과 미실행 검증을 구분한다. 완료 시점 종속 자동화를 만들지 않고 이 작업의 마무리 순서로 수행한다.

## 2026-11-21: 라우터 분리·build 산출물 통합
사용자가 경로 판별과 응답 내용 선택을 router.c로 분리하는 안을 선택했다. 비교 브랜치의 411·요청 Content-Type 반영 정책은 채택하지 않는다. http_route_request는 본문 수신 전 호출하고, router_prepare_response는 응답 시점에 기존 메모리를 빌려 참조한다. 파싱·수신·송신·FD/메모리 소유권과 오류 우선순위는 유지한다.
산출물은 build/server, build/obj/*.o, build/test_*로 통일한다. 기존 make 명령과 개별 테스트 빌드 별칭을 유지하고 검증 스크립트의 실행 파일 탐색을 프로젝트 기준 절대 경로로 바꾼다. build를 무시하고 이미 추적된 바이너리만 추적 해제한다. 커밋·푸시·과거 이력 재작성은 하지 않는다.
