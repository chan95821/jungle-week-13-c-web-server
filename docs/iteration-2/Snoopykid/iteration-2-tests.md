# Iteration 2 테스트 검토 초안

현재 상태: 기본 파서 단위 테스트와 기본 2단계 E2E 소스 준비, 기존 회귀 입력 갱신 및 컴파일/구문 확인 완료. 테스트 실행·성능 측정은 미실행이며 통과/실패를 판정하지 않았다. 아래 후보·선택 전 문구는 기록 시점의 이력이다.

## 1. 수신과 파싱의 분리

| 사례 후보 | 확인 목적 | 결정·실행 상태 |
|---|---|---|
| 헤더 전체만 도착 | 전체 수신 길이와 헤더 끝 위치 구분 | API 검토 후 구체화, 미실행 |
| 헤더 끝의 CRLFCRLF가 분할 도착 | recv 호출 경계를 넘어 종료 탐지 | 미실행 |
| 헤더와 본문 앞부분 동반, 나머지 나중 도착 | 이미 받은 본문을 버리거나 중복 수신하지 않음 | Content-Length 방식으로 확정, 수신 API 선택 후 구체화 |
| 헤더와 본문 전체 동반 | 불필요한 추가 recv 없이 정확한 본문 처리 | Content-Length와 octet-stream 고정으로 확정, API 선택 후 구체화 |
| 본문에 NUL·CRLFCRLF 포함 | 문자열 길이나 본문 내용으로 요청 경계를 오인하지 않음 | 미실행 |

| 선언 길이보다 많은 데이터 | 본문 경계와 다음/추가 데이터 분리 | 연결 종료·keep-alive 범위 선택 후 구체화 |

## 2. 요청 라인·필드·경로

- Method/URI/Version 분리, 잘못된 형식·공백·제어문자·긴 요청 대상: 지원 구문·상한·상태 코드 선택 후 사례 확정.
- HTTP/1.1의 유효한 단일 Host와 Host 누락·복수·잘못된 값의 400 처리. 경로의 Host 일치 검증 등 세부 범위는 별도 검토.
- Content-Length 0·양수·비숫자·부호·오버플로우·중복/충돌. 표준상 가능한 처리와 선택 가능한 정책을 구분해 결정.
- Content-Length/Transfer-Encoding 동시 존재, 미지원 전송 코딩, chunked: 지원 범위 선택에 맞춰 정상/거부 사례 작성.
- Expect: 100-continue: 수락 가능한 요청의 본문 대기 전 반응과 헤더만으로 거부할 수 있는 경우를 구분. 정책 선택 전 미실행.
- GET /hello와 POST /echo: 응답 타입·본문·길이는 사용자 확정 후 검사값 작성. echo는 받은 바이트와 길이를 기준으로 비교.
- 기존 GET / 회귀: 유지·변경 정책 선택 후 기대 응답 확정. 존재하지 않는 경로와 미지원 메서드의 처리도 별도 결정.

## 3. 기존 테스트와의 관계

- 기존 수신 함수의 out_len은 헤더 길이가 아닌 전체 수신 길이다. 새 인터페이스를 선택할 때 기존 단위 테스트 의미를 명시적으로 유지·변경한다.
- Host 없이 성공을 기대하는 기존 E2E 입력은 정상 Host 포함 사례와 누락 400 사례로 분리할 필요가 있다. 아직 수정하지 않았다.
- 일부 기존 E2E는 recv 한 번에 응답 전체가 온다고 가정한다. 응답 검증기도 스트림 수신을 고려하도록 검토해야 한다.
- 기존 기능 반복, EOF·reset·SIGPIPE, 포트 충돌·재시작·신호 종료·FD 회수는 회귀 후보이며 해당 테스트 실행을 자동 허락받은 것으로 보지 않는다.

## 4. 별도 보류

431 응답·호출별 5초 제한은 VERIFICATION.md의 미구현·미검증 필요 항목을 유지한다. 2단계 적용 여부·구현·테스트 작성은 별도 선택 후 진행한다. 크기·할당·backlog·타임아웃·최적화·동시성 비교와 계측·부하는 EXPERIMENTS.md의 추후 범위이며 지금 실행하지 않는다.
## 5. 이번 답변으로 확정된 검증 대상

- 유효한 Content-Length 길이의 본문을 /echo에서 그대로 반환하고 응답 Content-Type이 application/octet-stream인지 확인한다. 응답 Content-Length는 실제 반환 바이트 수와 일치해야 한다.
- 텍스트·NUL 포함 바이너리·줄바꿈·CRLFCRLF 포함 본문에서 바이트 일치를 확인한다. 헤더와 동반 수신된 본문을 보존하는 사례 및 분할 본문 사례를 포함한다.
- 요청 Content-Type을 달리해도 응답 타입은 고정한다. JSON 형식 검증·변환이나 압축 해제를 기대하지 않는다.
- Transfer-Encoding 및 chunked 요청은 이번 단계의 정상 수신 사례로 처리하지 않는다. 선택할 상태 코드에 따라 명시적 거부·종료를 검사한다. Content-Length와 Transfer-Encoding 충돌 사례의 기준도 별도 확정한다.
- chunked 지원·검증은 최종 소스 구현·검증 완료 시 재검토할 체크포인트에 남긴다. 아직 구현·실행하지 않는다.

## 본문 크기·길이 불일치 검증 후보 (2026-11-20)

- 본문 임시 상한 65,536바이트 기준 65,535 / 65,536 / 65,537바이트 선언과 실제 전송을 구분해 검증한다. 상한 초과는 큰 본문 할당·전체 수신 전에 거부하는 정책을 검토한다.
- Content-Length 10, 본문 5바이트 후 EOF: 불완전 요청이며 부족분을 채우거나 성공 echo하지 않는다. 오류 응답은 별도 확정한다.
- Content-Length 10, 본문 5바이트 후 연결 유지: 아직 전송 중인지 식별할 수 없다. 수신 완료 기한 및 타임아웃 정책을 선택 후 검증한다.
- Content-Length 10, abcde 뒤 GET으로 시작하는 데이터 추가: 앞의 10바이트가 본문이다. HTTP처럼 보이는 내용으로 경계를 다시 추측하지 않는다.
- Content-Length 5, abcde 뒤 추가 데이터: 현재 본문은 5바이트만이며 남은 바이트는 별도 데이터다. 같은 recv 동반·후속 recv 분할·정상 두 번째 요청 동반을 구분한다. 연결 재사용 및 종료 정책 선택 후 기대값을 확정한다.
- NUL·CRLFCRLF·요청처럼 보이는 본문도 바이트 기준 처리한다. 음수·비숫자·정수 오버플로우·상충 Content-Length와 Transfer-Encoding 충돌도 별도 정책으로 검증한다.
- 후보 문서화만 수행했다. 테스트 코드 작성·공식 검증·성능 측정은 실행하지 않았다.
## 확정 정책 기반 추가 검증 후보: 경계·본문 수명

- 본문 65,535·65,536바이트는 상한 내 수신·echo의 바이트 무결성 대상으로 하고, 유효한 Content-Length 65,537바이트는 전체 본문 수신·큰 할당 전 413 대상이다.
- 헤더·본문 동반 수신, 본문 다중 분할 수신, 선언 길이보다 짧은 전송 후 EOF와 연결 유지 상태를 각각 구분한다. 타임아웃·전체 기한은 별도 정책 확정 후 기대값을 작성한다.
- 선언 길이 뒤 추가 데이터와 정상 형식의 두 번째 요청이 붙은 경우, 현재 본문에는 선언 길이까지만 포함하고 두 번째 요청은 처리하지 않는다. 읽지 않은 데이터 배출·닫기 정책 확정 후 실제 응답 전달과 종료를 확인한다.
- 본문 내 NUL·CRLFCRLF·GET 문자열을 경계로 사용하지 않는다. Content-Length 형식·오버플로우·상한과 중복·충돌을 별개 사례로 다룬다.
- GET /와 /hello 모두 200·text/plain·Hello 5바이트이며 새 파서 검증을 통과해야 한다.
- 본문 0에서 malloc을 호출하지 않는지, 유효 양수 길이에서 한 번 할당하는지, 할당 실패 시 NULL 역참조·정상 echo가 없는지 확인한다. 오류 응답 코드는 별도 확정한다.
- 정상·EOF·수신 오류·송신 오류·종료 등 각 경로에서 연결 소유자가 한 번 free하고 빌려 쓰는 하위 함수가 중복 free하지 않는지 검토한다. 필요한 결정적 오류 주입과 sanitizer 실행 범위는 공식 검증 전에 제시한다.
- 위 내용은 사례 누적이며 테스트 코드·비교 실험·계측을 지금 구현하거나 실행하지 않는다.
## 추가 후보: 엄격한 길이 및 5·7·15초 기한 (2026-11-21)

- 잘못된 십진 길이·오버플로우·동일/상충 복수 Content-Length·쉼표 목록·Content-Length/Transfer-Encoding 충돌의 400 및 종료를 확인한다. 허용 정규화 성공 사례로 바꾸지 않는다.
- 유효 65,537바이트 선언은 큰 본문 할당·전체 수신 전 413, 헤더 상한 초과는 431, 할당 실패는 500의 기능 검사 후보다. 응답 실제 전달은 아직 미결정인 연결 종료 정책을 함께 검토해야 한다.
- 본문 조기 EOF는 가능한 경우 400이고 정상 echo하지 않는다. reset과 서버 종료는 응답 불가능·중단 상태로 구분한다.
- 수신·송신 호출별 5초와 전체 헤더 7초·본문 15초를 구분해 검사한다. 전체 헤더는 accept 시점, 본문은 헤더 수신 완료 시점부터이며 조각 도착·EINTR로 갱신하지 않는다.
- 무입력은 호출별 제한에 먼저 도달할 수 있고, 호출별 제한을 피하는 지속 소량 전송도 전체 기한에 따라 408 대상으로 끝나는지 확인한다. 스케줄링 여유·시계/오류 주입 및 테스트 실행 범위는 사전 검토 후 확정한다.
- 이는 제한시간 기능의 판정 후보이며 요청 지연·처리량 등 성능 계측 허락이 아니다. 서버 구현·테스트 코드 작성·공식 검증·성능 측정은 실행하지 않았다.
## 추가 후보: 단계적 종료와 100 Continue (2026-11-21)

- 정상 응답·413·431 등 응답 후 송신 방향 종료와 수신 EOF/폐기 기한/폐기 바이트 상한에 따른 최종 close를 구분해 확인한다.
- 미수신 추가 데이터와 파이프라인 형태의 입력은 폐기만 하고 두 번째 응답을 만들지 않는다. 64KiB 또는 1초에서 정리를 끝내며 지속 소량 전송이 폐기 기한을 갱신하지 않는지 확인한다.
- 순차 서버의 추가 점유 비용은 알고 있는 설계 한계로 기록한다. 처리량·응답 지연 계측과 비교 부하 실험은 이 기능 검사에 포함하지 않는다.
- 클라이언트가 끝내 닫지 않거나 계속 전송할 때 상한에 따른 종료 및 실제 응답 수신 여부를 구분한다. bounded drain만으로 응답 전달 보장을 주장하지 않는다.
- 폐기 대기 중 SIGINT/SIGTERM은 추가 폐기를 기다리지 않고 일반 경로에서 FD·본문 메모리를 정리해야 한다.
- Expect: 100-continue와 유효한 요청 헤더 후 본문이 아직 부족하면 100 응답을 받은 뒤 본문을 전송하는 클라이언트가 최종 echo를 받는지 확인한다.
- 헤더만으로 413 등 거부가 가능한 경우 100 없이 최종 오류를 보내는지, 본문 전체가 동반 수신된 경우 불필요한 100을 생략하는지 확인한다.
- 중간 응답과 최종 응답은 각각의 헤더 경계로 구분하고 100에는 본문을 기대하지 않는다. TCP 분할 수신에 대응하는 테스트 클라이언트가 필요하다.
- 후보 누적만 수행했으며 테스트 코드 작성·실행·성능 측정은 하지 않았다.
## 구현 전 기본 성공·실패 후보와 6단계 확대 범위

| 규칙 | 이번 기본 성공 후보 | 이번 기본 실패 후보 |
|---|---|---|
| 요청 라인·지원 범위 | HTTP/1.1 origin-form의 Method·target·Version 구분 | 잘못된 구문 400, 범위 밖 버전 505, 미지원 absolute-form 501 |
| URI | 쿼리 앞 경로 라우팅, 유효한 percent 구문을 원래 바이트로 보존 | 잘못된 percent 구문·fragment·공백·제어문자 400 |
| 필드·Host | 필드 이름 대소문자·OWS, 유효한 단일 Host, 의미 미지원 일반 필드 건너뜀 | Host 누락·중복·잘못된 값, colon 앞 공백·obs-fold·NUL·제어문자 400 |
| 본문 길이 | 길이 정보 없음과 명시적 0의 빈 echo, 양수 길이 정확 수신 | 비숫자·오버플로우·동일/상충 중복·쉼표 목록·CL/TE 충돌 400 |
| 입력 상한 | 헤더 8191/8192와 본문 65535/65536 | 헤더 초과 431, 유효 선언 길이 65537은 할당·전체 수신 전 413 |
| 본문 경계 | 헤더 동반·분할·NUL/CRLFCRLF 포함 바이트 echo, 뒤 추가 데이터 제외 | 부족한 EOF 400·수신 제한시간 408, 정상 echo 금지 |
| 명시적 미지원 | 정상 GET / 및 /hello, POST /echo | 경로 404, GET/POST 경로 불일치 405+Allow, 다른 메서드 501, 잘못된 TE 400/유효 chunked 미지원 501 |
| Expect | 본문이 더 필요할 때 100 후 최종 응답, 이미 완성된 본문은 100 생략 | 헤더만으로 413이면 100 없이 최종 오류, 미지원 Expect 417 |
| 소유권·종료 | 길이별 1회 할당·0 무할당·한 번 해제, 기본 폐기·신호 종료 | 할당 실패 500, I/O 오류·종료에서 중복 해제·FD 누수 방지 |

파서는 입력 헤더를 변경하지 않으며 참조가 원본 버퍼 범위 안에 있는지도 확인한다. 기본 테스트 소스는 구현과 함께 준비할 수 있지만 실행은 아직 허락되지 않았다.

6단계에서는 이 기본 세트를 대체하지 않고 퍼징·대규모 조합·다수 오류 주입 시점·장시간/경합/반복 장애와 전체 회귀를 확대한다. 지금 광범위한 검증·부하·성능 비교를 자동 추가하지 않는다.
## 현재 준비한 실행 범위와 미포함 항목

| 수단 | 준비한 내용 | 실행 상태 |
|---|---|---|
| make test | 기존 포트·수신 경계·완전 송신 단위 테스트 + test_http_parser의 기본 파싱·거부·경로 사례, sanitizer 옵션 | 컴파일만 성공, 미실행 |
| make verify | 1단계 회귀 + 기본 2단계 GET/echo, 빈·바이너리·분할·추가 데이터, 크기 경계, 기본 오류·100 Continue | Python 구문 확인만 성공, 미실행 |
| 추가로 범위 확정할 기본 검증 | 5/7/15초 제한의 제어된 재현, 1초/64KiB 폐기 상한, malloc 실패·종료 중 정리, 실제 partial send/EINTR의 결정적 재현·FD 회수 | 후보 문서화 상태. 기존 명령 실행만으로 모두 커버했다고 주장하지 않음 |
| Iteration 6 확대 | 광범위한 입력·분할·중복 조합/퍼징, 여러 오류 주입 시점, 장시간·신호/자원 경합·전체 회귀 | 이후 범위 |
| 성능/부하/비교 | 별도 지표·환경·조건·명시적 허락 대상 | 미구현·미실행 |

클라이언트가 Expect 헤더와 전체 본문을 send 한 번으로 보냈더라도 서버 recv가 한 번에 받았다고 가정하지 않는다. 해당 E2E는 정당한 100 유무를 모두 수용하고 최종 응답을 검사한다. 이미 전체 본문이 수신된 분기의 100 생략 자체는 제어된 수신 조건 또는 별도 단위 검증이 필요하다.

## 라우터 분리·build 경로 변경 검증 후보 (실행 미허가)
- 기존 경로/메서드/Allow 및 오류 우선순위를 유지한다.
- Hello는 text/plain·5바이트, echo는 application/octet-stream·바이너리 길이 및 원본 포인터를 유지한다. 빈 echo는 0바이트, 오류는 기존 상태 문구를 사용한다.
- 응답 준비 함수는 할당·해제·I/O 없이 입력 공간을 빌려 참조한다.
- 서버 및 네 개 테스트의 컴파일·링크와 산출물 위치를 확인한다. 실행 테스트와 성능 측정은 별도다.
- make test/verify, 반복·병렬 빌드·clean 후 재빌드와 기존 회귀의 공식 검증 범위는 실행 전 확정한다.
- build 무시 및 이전 바이너리 추적 해제는 Git 상태로 확인한다.
### 라우터 분리·산출물 통합 확인 결과
WSL에서 make all test_parse_port test_recv_header test_send_all test_http_parser를 실행해 서버(-O2)와 네 개 테스트(sanitizer 옵션)의 컴파일·링크에 성공했다. 테스트 바이너리는 실행하지 않았다. Python AST 구문 확인 성공. make -n test verify는 새 경로를 사용하며 실제 검증은 실행하지 않았다. Git diff --check는 공백 오류 없이 통과했고 LF/CRLF 경고만 있었다.
build/server·build/obj/main.o·build/test_send_all·build/legacy/webserver가 무시됨을 확인했다. server 및 세 기존 테스트 바이너리를 인덱스에서 제거했으며, 알려진 산출물은 더 이상 추적되지 않는다. 프로젝트 루트·src·tests/unit·scripts에서 ELF/객체 파일이 남아 있지 않음을 확인했다. 기존 webserver는 build/legacy에 보관했다. 커밋·푸시하지 않았고 다른 기존 staged 변경은 유지했다.
공식 기능 검증(라우팅/Allow·Hello/echo·오류 회귀), 반복·병렬/clean 후 재빌드 검증 및 성능 측정은 미실행이다.
