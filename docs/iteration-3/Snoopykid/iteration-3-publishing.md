# 정적 파일 게시의 신뢰 경계·운영 계약

이 문서는 필요한 조건을 설명한다. 현재 노트북·WSL·마운트의 권한이 조건을 만족한다고 확인한 결과가 아니다. 권한 자동 변경과 게시 스크립트는 이번 범위에 없다.

## 필요한 조건
- 서버는 전용 비특권 계정으로 정적 파일 읽기와 디렉터리 탐색만 가능해야 한다. 파일/부모 디렉터리 쓰기는 신뢰하는 게시자에게만 허용한다.
- 서버가 같은 계정의 파일 소유자이면 모드만 읽기 전용이어도 권한을 다시 바꿀 수 있다. 소유자·그룹·ACL·상위 디렉터리·마운트 및 Windows/WSL 권한 해석까지 검토해야 한다.
- 기존 inode를 직접 덮어쓰거나 truncate하지 않는다. 다른 하드링크/이미 열린 쓰기 FD로 같은 inode를 수정하는 행위도 제외한다.
- 요청 경로의 심볼릭 링크는 거절하지만, 설정한 루트의 링크는 시작 시 OS가 해석해 한 번 연다.
- 악의적인 디렉터리 이동/교체, 마운트 변경, 권한 있는 게시자의 악성 파일 게시까지 격리하는 서버가 아니다. 정적 트리 변경 권한은 신뢰 경계다.

## 새 파일 완성 후 rename 게시
1. 공개되지 않는 신뢰된 staging 디렉터리에 새 일반 파일을 작성한다. 목적 파일과 같은 마운트/파일시스템이어야 한다.
2. 쓰기를 완료하고 서버가 읽을 수 있는 소유권·권한·메타데이터 조건을 확인한 뒤 파일을 닫는다.
3. POSIX rename(또는 renameat)으로 완성된 파일을 최종 이름에 교체한다. 교차 파일시스템 rename은 실패하므로 복사 후 덮어쓰기로 자동 대체하지 않는다.
4. 이미 열어 전송 중인 FD는 이전 inode를 계속 읽고, 이후 열기는 새 파일을 얻는다. 이전/새 inode를 직접 수정하지 않는 조건이다.
5. 실패 시 기존 게시 파일을 보존하고 staging 파일 정리/재시도는 게시자가 책임진다. 디렉터리 구조를 요청 처리 중 악의적으로 이동·교체하지 않는다.

비용은 새 파일을 만드는 디스크 쓰기와 임시 공간, 게시 권한 분리, 메타데이터 관리다. rename의 이름 교체 원자성과 재부팅 후 데이터 내구성은 다르다. 후자까지 필요하면 파일/디렉터리 동기화·복구 절차를 별도 설계해야 한다.

이 절차나 스냅샷은 파일 내용이 안전하다는 검증이 아니다. 신뢰하는 게시자가 악성 HTML/JS 등 콘텐츠를 게시하는 문제를 방지한다고 주장하지 않는다.

## 서버의 파일 변경 실패 정책
최초 fstat 크기까지만 송신한다. 증가분은 제외하고 조기 EOF/읽기 실패/송신 실패는 로그 후 연결·파일 FD를 정리한다. 이미 헤더를 보낸 뒤 두 번째 오류 응답을 붙이지 않는다. 동일 크기 덮어쓰기는 감지하지 않아 내용이 섞일 수 있다.

## 검증 후보
실제 서버/게시자 계정의 소유권·그룹·ACL·파일 읽기/쓰기·디렉터리 탐색/쓰기, 마운트 환경을 확인한다. 임시 fixture에서 읽기 거절·초기 루트 실패·새 파일 rename 후 기존 FD/새 FD 차이, truncate/read/send 오류 후 안전한 실패와 FD 회수를 검증한다. 공식 실행 범위는 별도 확정한다.
