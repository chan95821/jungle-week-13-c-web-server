# Iteration 3 요구사항 논의

상태: 논의 중. 아래는 개인 브랜치의 결정과 미결정 사항이며 구현 또는 검증 완료를 뜻하지 않는다.

## 기준

- [Issue #3](https://github.com/chan95821/jungle-week-13-c-web-server/issues/3): 정적 파일과 서버 내부 동적 응답, 기존 GET /hello 및 POST /echo 유지.
- 과제 원문: `docs/requirements/web-server.md`. 팀 진행 기준: `docs/DEVELOPMENT_CONTEXT.md`.
- 팀 체크포인트에서 개인 구현을 비교하며, 이 문서는 팀 통합 기준이 아니다.

## 방향과 데모

- 학습을 우선한다. 실제로 브라우저에서 사용하면서 정적 파일 응답, 주소와 파일의 대응 관계, 입력에 따라 달라지는 동적 응답을 이해한다.
- 카페 소개와 메뉴를 볼 수 있고 이름을 입력해 환영 인사를 받는 데모를 논의 기준으로 한다.
- 동적 데모는 입력한 이름이 반영된 HTML이다. 이름은 인증된 신원이 아니다. 범용 템플릿 엔진과 인증은 확정 범위가 아니다.
- CGI와 별도 백엔드 전달은 Issue #3의 필수 범위가 아니며 Reverse Proxy는 Iteration 4에서 다룬다.

## 이번 작업의 흐름 기준선

- 사용자 지시: 정적 범위의 합의된 흐름을 기준으로 테스트 코드와 구현을 각각 병렬 작업하고 이후 기능·회귀 테스트를 실행한다. 동적 환영 페이지와 성능 측정은 포함하지 않는다.
- 서버 시작 → 상대 정적 루트 검증 → 요청 수신·파싱 → 메서드·경로 라우팅 → 본문 수신 → 선택된 처리 함수의 응답 준비 → 본문 제공자를 통한 길이 기준 전송 → 제공자·연결 정리.
- 정적 처리: 지정 페이지 또는 `/assets/...` 경로 → 지원 MIME과 허용 경계 검토 → 파일 열기와 일반 파일 확인 → 파일 본문 제공자. 실패는 합의된 개인 정책에 따른다.
- 응답 전송과 제공자 정리는 하나의 내부 흐름이 맡는다. 전송 성공·실패와 무관하게 정리 함수가 있으면 한 번 호출하고, 실패 시 전송 오류를 보존한다. 연결 종료 처리와 요청 본문 해제는 `handle_client()`가 계속 맡는다.
- 오류 우선순위·검증 주입 방법은 이 기준선으로 확정하지 않는다. 기존 팀 기준과의 차이 및 `realpath()`/열기 사이 경쟁 상태의 한계는 그대로 유지한다.
- 사용자는 데모 구성을 구현자에게 맡겼다. 이번 개인 데모는 작업 디렉터리 기준 `public`을 정적 루트로, `/cafe`와 `/menu`는 각각 `pages/cafe.html`, `pages/menu.html`에 대응한다. 리소스는 `public/assets/`에 둔다. 이는 CLI·설정 루트를 요구하는 팀·과제 기준을 변경하지 않는다.

## 확정된 정적 경로 방향

| 공개 요청 경로 | 의도 | 근거 |
|---|---|---|
| `/cafe` | 지정된 카페 소개 HTML 제공 | 파일 경로와 다른 사용자 친화적 페이지 주소를 경험 |
| `/menu` | 지정된 메뉴 HTML 제공 | 같은 방식의 실제 사용 흐름 |
| `/assets/...` | 지정된 정적 루트 아래 `assets/...` 파일에 공통 대응 | CSS·이미지 등 여러 리소스를 같은 규칙으로 제공 |
| `/pages/...` | 파일 경로에 자동 대응하지 않음 | 공통 파일 대응 규칙은 `/assets/...`에만 적용 |

- 예시: 정적 루트가 `public`일 때 `/assets/logo.png`는 `public/assets/logo.png`에 대응한다. `public`은 예시이며 실제 루트는 지정해야 한다.
- `/cafe`, `/menu`의 개인 데모 파일명은 위 작업 기준선을 따른다. 파일의 존재만으로 URL이 자동 등록되지 않는다.
- 등록되지 않은 경로는 현재 라우터의 404 정책을 유지한다. 기존 `/`, `/hello`, `/echo`와의 충돌 및 회귀를 검토한다.
- HTML이 CSS·이미지를 참조하면 브라우저가 각 리소스를 별도 요청한다. Velog의 공개 HTML에서도 페이지와 별도 CSS·JavaScript 주소를 확인했으나 서버 내부 파일 대응 방식은 확인하지 못했다.

## 공통 요구사항 및 경계

- 정적 루트는 CLI 또는 설정으로 지정한다. 구체적인 입력 방식은 미정이다.
- 팀 기준 변경 제안: 사용자는 CLI·설정으로 루트를 지정하는 대신 코드에 고정하는 방향을 제안했다. 현재 Issue #3과 충돌하며 팀 승인·이슈 변경 전이다. 실행 위치에 따른 경로 해석, 다른 테스트 루트 사용 및 이식성은 별도 논의한다. 코드나 팀 이슈는 아직 변경하지 않았다.
- 개인 설계 방향: 코드에 고정한 상대 경로를 서버 프로세스의 현재 작업 디렉터리 기준으로 해석한다. 프로젝트 루트에서 실행하며 이번 데모 루트는 `public`이다.
- 사용자 결정: 시작 시 정적 루트만 존재하는 디렉터리인지 확인한다. 유효하지 않거나 권한 등으로 확인할 수 없으면 이유를 출력하고 서버를 시작하지 않는다. 별도의 접근 권한 사전 확인은 하지 않는다. `assets`와 개별 데모 파일의 존재·접근은 시작 조건으로 삼지 않으며 요청 시 처리한다. 구체 오류 보고는 별도 논의한다.
- HTML, CSS, JS, PNG, JPG 등의 MIME 유형과 실제 바이트 수의 Content-Length를 제공한다.
- 바이너리 내용을 바이트 단위로 정확히 전달하며 큰 파일도 버퍼 크기와 무관하게 처리한다.
- 파일 없음·접근 불가·서버 오류 등에 기본 오류 응답을 제공한다. 구체적 구분과 우선순위는 미정이다.
- 팀 Issue #3은 `../`, 인코딩, 심볼릭 링크 등을 통한 정적 루트 밖 접근 방지를 요구한다.
- 이전 개인 선택: 심볼릭 링크를 따라간 대상이 정적 루트 밖이어도 주소 기준으로 제공하기로 했으나 팀 Issue #3의 완료 조건과 충돌했다. 아래 후속 결정이 이 선택을 대체한다.
- 후속 사용자 결정: `/assets/...` 요청은 심볼릭 링크 자체를 일괄 거부하지 않되, OS가 경로와 링크를 해석한 최종 대상이 정적 루트 아래 `assets` 영역 안에 있어야 제공한다. 영역 밖 대상의 외부 응답은 후속 결정에 따라 404다. 기존 외부 링크 대상 허용 선택은 철회한다. 이는 팀 Issue #3의 루트 탈출 방지 방향과 부합하나, 실제 구현·검증은 미완료다.
- 정적 루트 밖 경로 접근도 외부에는 404로 응답한다. `..` 등의 경계 판단과 탐지·처리는 아직 논의 중이다.
- 사용자 결정: 정적 서빙은 지원 MIME 확장자로 매핑되는 일반 파일만 제공한다. 미등록 확장자나 일반 파일이 아닌 대상은 공통 404로 처리한다. MIME은 확장자로 선택하며 파일 내용이 실제 형식과 일치하는지 검증하지 않는다. 이 제한은 `realpath()` 확인과 열기 사이의 경쟁 상태를 해결하지 않는다.
- 사용자 결정: 확장자 매핑은 대소문자를 구별하지 않는다. `.html`은 `text/html`, `.css`는 `text/css`, `.js`는 `text/javascript`, `.png`는 `image/png`, `.jpg`·`.jpeg`는 `image/jpeg`다. 문자셋 표기 등 추가 세부값은 미정이다.
- 사용자 결정: 요청 주소의 `..` 경로 요소는 일괄 거부하지 않고, 경로 해석 결과가 `assets` 영역 안이면 허용하고 밖이면 거부하는 방향이다. 구체적인 해석 기준은 아래 후속 결정을 따른다.
- 후속 사용자 결정: 심볼릭 링크와 `..`이 함께 있으면 문자열에서 `link/..`을 먼저 상쇄하지 않고 OS의 파일 시스템 경로 해석 의미를 기준으로 한다. 최종 대상이 `assets` 영역 안에 있어야 하며, 대상 부재와 영역 밖은 모두 외부에 404로 응답한다.
- 사용자 결정: 이식성과 학습 단순성을 위해 POSIX `realpath()`로 경로를 해석·경계 확인한 후 별도로 파일을 여는 방식을 선택한다. 파일 열기·읽기 가능 여부는 후속 처리에서 확인한다. 단 `realpath()` 자체도 대상 부재·권한 등으로 실패할 수 있다. 경로 확인과 파일 열기 사이 심볼릭 링크 등이 바뀌면 경계가 깨질 수 있으며, 이 경쟁 상태에 대한 보안 보장은 없다. 이 제한 때문에 팀 Issue #3의 경로 탈출 방지를 경쟁 상황까지 충족했다고 주장할 수 없고 팀과 범위 확인이 필요하다.
- 사용자 동의: 정적·동적 라우팅과 이후 Reverse Proxy에서 주소 해석의 일관성을 고려한다. 원본 주소 보존, 백엔드 전달 형태 및 백엔드와의 해석 차이 처리 정책은 아직 결정하지 않았고, 프록시 구현을 이번 단계에 포함하지 않는다.
- 사용자 결정: 정적 파일 요청의 경로에 인코딩된 슬래시 `%2F`가 있으면 거부한다. 일반 슬래시를 사용하면 되며 경로 경계의 해석을 단순하게 유지하기 위함이다. 이 결정은 다른 인코딩 전체의 거부나 동적·프록시 요청에 대한 전역 정책을 뜻하지 않는다. 구체적 오류 상태와 검출 시점은 미정이다.
- 후속 사용자 결정: `/assets/...`로 분류되는 정적 리소스 요청은 경로 부분에 유효한 퍼센트 인코딩이 하나라도 있으면 거부한다. 앞선 `%2F` 거부를 포함하는 더 넓은 정책이다. 공백·한글·퍼센트 등 인코딩이 필요한 리소스 파일명은 이 범위에서 지원하지 않는다. 쿼리, 페이지 별칭·동적·프록시 경로는 이 결정에 자동 포함하지 않는다. 오류 상태와 검사 시점은 미정이다.
- 사용자 결정: `/assets/` 접두사는 디코딩하지 않은 원본 경로 기준으로 판단한다. 따라서 `/%61ssets/logo.png`는 현재 정적 리소스 경로가 아니며 미등록 경로의 404 정책을 따른다. 향후 프록시가 미등록 경로를 전달할 경우 백엔드와의 해석 차이는 Iteration 4에서 별도 검토한다.
- 사용자 결정: `/assets/...`로 분류된 정적 리소스 경로에 유효한 퍼센트 인코딩이 있으면 400으로 거부한다. 인코딩 자체가 잘못된 URI 문법이라는 뜻이 아니라 이 프로젝트가 해당 정적 경로 형태를 지원하지 않는다는 정책이다. 잘못된 퍼센트 구문도 현재 요청 파서에서 400이다. 검사 시점은 미정이다.
- 이전 사용자 결정: 정적 파일이 없으면 404, 파일에 접근할 수 없으면 403, 그 밖의 서버 내부 오류는 500으로 구분했다. 아래 후속 결정이 외부 응답 정책을 대체한다.
- 후속 사용자 결정: 정적 파일 없음, 접근 불가, 허용 영역 밖 대상은 외부에 모두 404로 응답한다. 파일 존재·접근 권한을 응답 코드만으로 구별하기 어렵게 하려는 목적이다. 유효하지만 지원하지 않는 인코딩 경로의 400과 그 밖의 서버 내부 오류 500은 유지한다. 내부 원인 기록은 미정이며 시간 차이 등 잔여 노출이 가능하다.
- 사용자 원칙: 클라이언트가 파일 부재·접근 불가·허용 영역 밖이라는 내부 사유를 구분하지 못하도록 세 경우의 외부 404 본문과 관련 응답 헤더를 동일하게 한다. 응답 코드·내용만으로 완전한 비노출이 보장되는 것은 아니며 시간 차이 등 잔여 노출을 고려한다. 서버 내부 원인 기록은 별도 논의한다.
- 팀 기준과 차이: Issue #3 완료 조건은 접근 불가 경로에 403을 명시한다. 개인 선택인 404 통일은 해당 완료 조건과 충돌하며, 팀 기준은 변경되지 않았다. 적용 방향은 팀과 별도 논의해야 한다.
- 사용자 결정: 정적 파일 응답을 시작한 뒤 읽기 오류가 발생하면 전송을 중단하고 연결 및 관련 자원을 정리한다. 기존 응답에 새 오류 응답을 이어 붙이거나 성공적으로 완료된 것으로 취급하지 않는다. 이미 전달된 상태 코드를 변경할 수 없으며, 선언한 본문 길이보다 일찍 종료되면 클라이언트가 불완전한 응답으로 판단할 수 있다.
- GET /hello 및 POST /echo의 기존 동작을 유지한다. 팀 기준의 현재 상태는 실제 소스와 별도 검증 결과를 구분한다.

## 미결정 및 후속 논의

- `realpath()`와 파일 열기 사이 변경에 따른 경계 이탈 위험은 개인 선택의 명시적 제한이다. 팀 이슈의 보장 수준과 적용 방향 확인, 실패 분류 및 경계 비교 세부사항은 미정이다.
- 접근 불가 시 개인 404 정책과 팀 Issue #3의 403 완료 조건 차이 해소. 서버 내부 원인 기록 정책.
- 퍼센트 인코딩, 심볼릭 링크, 디렉터리 요청, 지원 메서드 및 경로 충돌 처리.
- MIME 미인식 파일의 처리와 지원 범위 세부사항.
- 동적 환영 페이지(`GET /greet`), 외부 CGI(`GET /cgi-bin/order`) 및 `Transfer-Encoding: chunked` 설계는 별도 동적 문서([iteration-3-dynamic-requirements.md](iteration-3-dynamic-requirements.md))에서 확정한다. 이 문서는 정적 서빙 범위의 결정·검증 기록으로 유지한다.
- 정적 파일 응답 준비·전송 및 자원 정리의 책임과 구체 설계.
- 추가 테스트 경계·장애 주입 및 팀 통합 검증 범위·시점. 이번 대화의 기능·단위 검증은 아래 결과를 따르며 성능 측정은 실행하지 않았다.

## 라우터 설계 결정

- 사용자 결정: 라우팅 규칙을 배열로 한곳에서 관리하고, 현재 필요한 정확 일치와 접두사 일치만 지원하는 방향으로 설계한다. 범용 정규식 매칭은 포함하지 않는다.
- `/cafe`·`/menu`와 `/assets/...`는 주소 매칭 및 파일 대응 규칙은 다르지만 별도의 정적 페이지·리소스 응답 종류로 나누지 않고 공통 파일 응답으로 다룬다.
- 기존 `http_route_request()`는 변경 전 조건문 기반이었고 본문 수신 전에 호출된다. 정적 경로의 허용 메서드와 파일 대상 정보 전달 방식은 미정이다.
- 사용자 결정: 여러 경로 규칙이 일치하면 가장 긴 경로 일치를 우선한다. 길이가 같고 정확 일치와 접두사 일치가 겹치면 정확 일치가 우선한다. 접두사 일치 판단은 탑다운으로 별도 함수 책임으로 분리해 설계한다. 메서드와의 관계는 아래 후속 결정을 따른다.
- 사용자 결정: 같은 메서드·경로·매칭 방식의 중복 규칙은 허용하며 배열에서 먼저 등록된 규칙이 우선한다. 중복을 서버 시작 오류 또는 금지 조건으로 취급하지 않는다.
- 사용자 결정: 접두사 매칭은 등록된 문자열을 그대로 비교한다. 경계가 필요하면 `/assets/`처럼 규칙 자체에 `/`를 포함한다. `/assets` 자체는 미등록 경로다.
- 사용자 결정: 디렉터리 자체는 정적 파일로 제공하지 않고 404로 처리한다. `/assets`는 접두사 불일치로 미등록 404, `/assets/`는 경로는 일치하지만 디렉터리이므로 404다. 디렉터리 목록과 기본 파일 제공은 범위 밖이다.
- 후속 사용자 결정: 메서드와 경로가 모두 일치하는 규칙을 후보로 모은 뒤, 그중 가장 긴 경로 규칙을 선택한다. 더 긴 경로의 메서드가 일치하지 않으면 더 짧은 경로 규칙이 선택될 수 있다. 동률 처리 기준은 앞선 결정을 따른다.
- 사용자 결정: 501·405·404를 구분하는 기존 오류 방향을 유지한다. 미지원 메서드와 경로는 존재하지만 해당 메서드로 처리할 수 없는 경우 및 미등록 경로를 구분하고, 405에는 Allow를 포함한다. 오류 우선순위는 별도 확인한다.
- 사용자 결정: 405의 Allow는 요청 경로에 일치하는 모든 정확 일치·접두사 규칙의 허용 메서드를 중복 없이 모아 구성한다. 짧은 접두사 규칙도 실제 라우팅에서 해당 메서드를 처리할 수 있으므로 포함한다. 구체적 탐색·표현 방식은 미정이다.
- 사용자 설계 방향: 각 라우트에 대응하는 처리 함수를 선택한다. 라우트 선택은 기존과 같이 본문 수신 전에 수행하고, 본문 수신 후 해당 함수를 실행하는 흐름을 검토한다.
- 사용자 결정: 매칭 성공 시 선택된 라우트 처리 함수가 응답을 준비하고, 라우팅 실패 시에는 라우트 함수 대신 공통 오류 응답을 준비한다. 두 결과 모두 공통 본문 전송 흐름을 사용한다.
- 현재 구현: `http_select_handler()`가 Hello·Echo 및 정적 처리 함수를 선택하며 `handle_client()`가 본문 수신 후 호출한다. 중복된 라우트 enum과 이를 사용하던 `http_route_request()`·`router_prepare_response()`는 제거했다. 각 핸들러가 성공 응답을, `router_prepare_error()`가 오류 응답을 준비한다.
- 사용자 결정: 라우트 처리 함수는 응답을 준비하고 실제 전송은 `handle_client()`가 조율한다. `handle_client()`는 메모리 본문과 파일 본문 등 여러 전송 방식을 다룰 수 있어야 한다. 구체적인 응답 표현과 파일·자원 소유권은 미정이다.
- 이전 사용자 결정: 기존 응답 표현을 출발점으로 본문 종류를 enum으로 구분하기로 했으나, 아래 후속 설계 방향으로 재검토한다.
- 후속 사용자 결정: enum 분기 대신 본문 제공 함수와 상태를 통해 반복적으로 전송할 내용을 제공하는 공통 흐름을 사용한다. 본문 전체를 slice로 제한하지 않으며 소켓 전송은 `handle_client()`가 담당한다. 제공자별 자원 정리를 위해 공통 정리 함수를 호출하는 조율은 가능하지만 `handle_client()`가 파일 등 구체 자원을 직접 알아서는 안 된다. 본문 제공·정리 함수의 구체 계약과 소유권은 미정이다.
- 사용자 결정: 제공자의 정리 함수는 정리할 자원이 없으면 NULL일 수 있다. `handle_client()`는 정리 함수가 있는 경우 성공·실패 경로에서 호출을 조율하고, 구체 자원은 알지 않는다.
- 사용자 결정: 응답 준비 성공 시 완성된 본문 제공자의 정리 책임을 `handle_client()`에 전달한다. 준비 중 실패하면 처리 함수가 확보한 자원을 정리한다. 준비 성공 후 헤더 전송 실패·본문 실패·연결 종료를 포함한 종료 경로에서 정리 함수가 있으면 정확히 한 번 호출한다.
- 사용자 결정: 본문 제공자의 정리는 응답 전송 직후 수행하며, 성공 시 `finish_response()`의 연결 종료 처리보다 먼저 수행한다. 전송 오류 정보가 정리 과정에서 덮이지 않도록 보존한다.
- 사용자 결정: 본문 제공 함수는 위치와 양수 길이의 바이트 조각, 완료, 오류를 구분한다. 제공된 바이트는 다음 제공 함수 호출 전까지 유효하다. `handle_client()`는 현재 조각을 완전히 전송한 뒤에만 다음 조각을 요청하며, 전송 실패 시 더 호출하지 않고 정리한다. `/echo` 등 빌린 요청 본문의 수명은 전송과 제공자 정리가 끝날 때까지 유지한다.
- 사용자 결정: 본문 제공자가 반환한 조각이 응답의 선언된 Content-Length 중 남은 바이트보다 크면, 그 조각을 일부만 전송하거나 초과분을 무시하지 않고 오류로 처리한다. 이미 응답이 시작된 경우 중단·정리한다.
- 사용자 결정: 선언된 Content-Length보다 일찍 제공자가 완료하면 불완전한 응답으로 처리하고 중단·정리한다. Content-Length가 0이면 본문 제공 함수를 호출하지 않고 정리 단계로 간다.
- 사용자 결정: 선언된 Content-Length를 모두 전송하면 본문 제공 함수를 다시 호출하지 않는다. 따라서 마지막 조각의 초과는 감지하지만, 정확히 길이를 채운 뒤 추가 조각이 있었을 가능성은 검사하지 않는다.

### 본문 제공 함수 계약

- 목적: 본문 전체의 출처를 노출하지 않고 반복 호출로 다음에 전송할 바이트를 제공한다. `handle_client()`가 소켓 전송을 조율한다.
- 입력: 제공자가 준비한 진행 상태. 구체적인 C 타입·함수명·함수 시그니처는 미정이다.
- 결과: 양수 길이의 바이트 조각, 정상 완료, 오류를 구분한다. 조각은 데이터 위치와 바이트 길이를 제공하며 다음 제공 함수 호출 전까지 유효하다.
- 호출 순서: 현재 조각을 완전히 전송한 뒤 다음 조각을 요청한다. 소켓 전송 실패 후에는 제공 함수를 다시 호출하지 않는다.
- Iteration 3 전송 정책: 이번 범위에서는 응답 전송 전에 Content-Length를 안다. 제공자가 남은 길이보다 큰 조각을 반환하면 그 조각은 전송하지 않고 오류로 중단한다. 선언 길이보다 일찍 완료하면 불완전한 응답으로 중단한다. 정확히 선언 길이를 전송하면 추가 호출 없이 종료한다. 길이 0이면 제공 함수를 호출하지 않는다. 이는 본문 제공자의 공통 계약이 항상 길이를 알아야 한다는 뜻이 아니다.
- 정리: 응답 준비 성공 시 정리 책임을 `handle_client()`에 전달한다. 준비 중 실패한 자원은 준비한 쪽이 정리한다. 준비 성공 후 종료 시 정리 함수가 있으면 정확히 한 번 호출한다. 정리 함수는 NULL일 수 있으며 구체 자원은 제공자가 관리한다.
- 데이터 수명: 빌린 요청 본문 등 제공자가 참조하는 데이터는 본문 전송과 제공자 정리가 끝날 때까지 유지한다.
- 범위: 정적 서빙 범위에서는 chunked와 사전에 길이를 알 수 없는 스트림을 사용하지 않는다. 동적 CGI 스트리밍을 위한 `Transfer-Encoding: chunked` 확장은 [iteration-3-dynamic-requirements.md](iteration-3-dynamic-requirements.md)에서 다룬다. 구체적인 내부 오류 보고·함수 시그니처는 정적 단계 기준이다.
- 현재 구현: `src/router.h`의 공통 `body_provider`를 라우트 처리 함수와 공통 오류 응답이 준비하고 `src/server.c`의 `send_body()`가 사용한다. 메모리 제공자는 응답 객체 내부 상태를 참조하므로 객체 주소를 정리 완료까지 유지한다. 정적 파일 제공자 및 카페 데모가 추가되었다.
- 사용자 작업 방식: 동적 서빙 논의는 보류하고 정적 범위에서 흐름을 구현하며 함께 검토한다. 이후 사용자 요청에 따라 정적 외부·단위 테스트를 작성하고 검증을 실행했다. 성능 측정은 요청하지 않았다.
- 라우터 상위 흐름 구현: `src/router.c`에서 배열에 기존 및 정적 경로를 등록하고 정확·접두사 매칭 책임을 분리했다. 일치하는 모든 경로의 메서드를 수집하고 메서드까지 일치하는 가장 긴 후보를 고른다. 같은 길이에서는 정확 일치가 접두사 일치에 우선하고 동일 규칙의 중복은 먼저 등록된 규칙이 우선한다. 동적 환영 처리는 추가하지 않았다.

### 이번 대화에서 실행한 검증

- `make test`: ASan·UBSan 단위 테스트 통과. 새 정적·제공자 테스트 포함. 모든 제공자 실패 주입·라우트 겹침을 검증한 것은 아니다.
- `make verify`: 기존 Iteration 1·2 기능 검증 스크립트 통과. 해당 스크립트의 범위 밖 장애·부하 조합까지 통과한 것은 아니다.
- `python3 scripts/verify_iter3.py --root public --cafe pages/cafe.html --menu pages/menu.html`: 정적 파일, MIME, 고정 파일 구성의 경계, 개인 접근 불가 404 및 기본 회귀 확인 통과. 링크 경합·동적 환영·부하·내부 장애 주입은 검증하지 않았다.
- 접근 불가 404·고정 루트는 팀 이슈/과제 기준과 차이가 남는다. `realpath()` 검사와 열기 사이 경쟁 상태에 안전하다는 증거가 아니다. 성능 측정은 하지 않았다.

## 논의 방식

- 사용자는 빠짐없이 판단할 수 있도록 이후 논의를 구조화해 진행하기를 요청했다.
- 전체 흐름에서 현재 논의 위치를 밝히고, 정상·오류·경계 상황, 앞선 결정과의 의존성, 남은 미결정 사항을 구분한다. 한 번에 모든 세부 정책을 확정하지 않는다.
