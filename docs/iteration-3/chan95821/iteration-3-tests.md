# Iteration 3 정적 서빙 테스트 기준

이 문서는 개인 정적 서빙에서 검증해야 할 동작과 경계 사례를 정의한다. 실행 결과나 구현 완료 상태는 기록하지 않는다.

## 라우터 — `http_select_handler()`와 `select_rule()`

- 등록된 정확 일치 경로는 그 경로에만 매칭한다. 경로의 앞부분만 같은 다른 주소는 매칭하지 않는다.
- `/assets/` 접두사는 해당 하위 경로에 매칭하고 `/assets-old/` 같은 다른 접두사에는 매칭하지 않는다.
- `/cafe`, `/menu`, `/assets/...`는 정해진 주소 대응에 따라 파일 응답을 제공한다. 내부 함수나 파일 구성은 검증 조건으로 삼지 않는다.
- 기존 `/`, `/hello`, `/echo`의 동작과 메서드별 성공·오류를 유지한다.
- 원본 접두사 `/%61ssets/...`는 `/assets/`와 매칭하지 않고 현 단계 미등록 경로로 처리한다.
- 여러 경로 규칙이 같은 요청에 일치할 때 더 긴 경로 규칙이 우선한다. 정확 일치·접두사 일치 각각이 포함된 사례와 여러 접두사가 겹치는 사례를 확인한다.
- 긴 경로의 메서드는 불일치하지만 짧은 접두사의 메서드와 경로가 일치하면 짧은 접두사 규칙이 선택된다.
- 후보가 없는 경우 미지원 메서드의 501, 경로는 있으나 허용되지 않은 메서드의 405 및 Allow, 미등록 경로의 404를 구분한다.
- 405 Allow는 일치하는 정확 경로와 모든 접두사 규칙의 메서드를 중복 없이 포함한다. 메서드 순서가 아닌 집합을 비교한다. 서버가 지원하지만 해당 경로에서 미허용인 요청 메서드를 사용하며 현재 미지원 메서드의 501과 혼동하지 않는다.
- 같은 길이의 정확 일치와 접두사 일치가 겹치면 정확 일치가 우선한다. 복수 오류의 우선순위가 미결정인 사례는 특정 결과를 강제하지 않는다.

## 라우트 등록 중복

- 같은 메서드·경로·매칭 방식의 중복 규칙이 있다면 먼저 등록된 처리 대상이 선택되는지 확인한다. 중복 자체는 오류가 아니다.

## 범위와 판정 원칙

- 이 문서는 개인 브랜치의 **정적 서빙·기존 기능 보존** 기준이다. 팀 전체의 완료 조건과 구분한다.
- 동적 환영 페이지·Reverse Proxy·chunked·길이를 모르는 스트림·성능 측정은 이 문서의 현재 검증 범위에서 제외한다.
- 성공·오류 결과와 관찰 가능한 계약을 우선한다. 함수 이름, 파일 분리, 버퍼 크기, 특정 syscall이나 호출 횟수 같은 내부 표현은 계약상 필요한 경우를 제외하고 고정하지 않는다.
- 문서의 함수·함수 포인터 이름은 현재 코드에서 관련 위치를 찾기 위한 표기이며, 이름 자체를 변경 불가능한 테스트 조건으로 만들지 않는다.
- 팀 Issue #3의 접근 불가 403과 개인 404 정책, 과제·이슈의 루트 설정 요구와 고정 루트 제안은 미해결 차이다. 개인 정책 통과를 팀 조건 통과로 간주하지 않는다.
- 현재 선택한 `realpath()` 확인 후 열기 방식은 그 사이 경로 변경에 대한 방어를 보장하지 않는다. 호출 자체를 테스트 조건으로 고정하지 않으며, 고정된 파일 구성에서의 경계 검증과 경쟁 상황의 보안 보장을 혼동하지 않는다.
- 개인 데모의 정적 루트는 작업 디렉터리 기준 `public`이고, `/cafe`와 `/menu`는 각각 `pages/cafe.html`, `pages/menu.html`에 대응한다.

### 팀 Issue #3과의 대조

- 동적 핸들러·입력 변화와 정적/동적 분기는 팀 완료 조건이지만 이 문서의 정적 범위 밖이다. 이 문서만으로 Iteration 3 전체의 완료를 판정하지 않는다.
- CLI·설정 기반 루트는 팀과 과제 요구지만 개인 고정 루트 제안과 충돌한다. 팀 합의는 아직 없다.
- 접근 불가 403은 팀 완료 조건이지만 개인 404 정책과 충돌한다. 팀 기준 변경은 확인되지 않았다.
- Issue #3 본문은 심볼릭 링크를 통한 탈출 방지를 요구한다. [사용자 코멘트](https://github.com/chan95821/jungle-week-13-c-web-server/issues/3#issuecomment-7078288910)는 링크 방지가 필요 없다는 의견이므로 의미와 팀 최종 기준을 확인해야 한다. 현재 개인 정책은 내부 링크 허용·영역 밖 차단이다.
- 파일 내용·MIME·기존 기능 회귀·파싱과 응답의 책임 분리는 팀 요구다.

## 시작 및 정적 루트 — 개인 고정 루트 정책

- 프로젝트 루트에서 실행할 때 지정된 상대 정적 루트가 존재하는 디렉터리라면 루트 검사 때문에 시작을 거부하지 않는다.
- 루트가 없거나 일반 파일인 경우 시작 실패를 알리고 요청을 수락하지 않는다. 루트의 디렉터리 여부를 확인할 수 없는 경우에도 실패한다.
- 루트가 유효하고 `assets` 또는 개별 데모 파일이 없어도 그 부재만을 이유로 시작을 거부하지 않는다. 실제 요청은 별도로 처리한다.
- 시작한 서버에서 지정 페이지 파일이 없으면 해당 페이지는 404이며, 이후 기존 `/hello` 요청도 처리할 수 있다.
- 실행 위치를 달리하면 현재 작업 디렉터리 기준으로 상대 루트를 해석한다. 접근 권한 사전 검사는 요구하지 않는다.

## 파일 응답과 MIME — `prepare_cafe()`, `prepare_menu()`, `prepare_assets()`, `prepare_file()`, `file_type()`

- `/cafe`, `/menu`는 각자 지정된 HTML 파일의 내용을 제공한다. `/pages/...` 형태로 자동 공개되지 않는다.
- `/assets/` 아래의 중첩된 허용 파일 요청은 정적 루트 아래 `assets`의 대응 파일을 제공한다.
- 지원 확장자 `.html`, `.css`, `.js`, `.png`, `.jpg`, `.jpeg`에 각각 `text/html`, `text/css`, `text/javascript`, `image/png`, `image/jpeg`, `image/jpeg` 유형을 제공한다. 유형 비교에서는 아직 미정인 charset 파라미터를 강제하지 않는다.
- 대문자·혼합 대소문자 확장자를 같은 유형으로 취급한다. 미등록 확장자와 확장자 없는 일반 파일은 공통 404다.
- 바이너리의 NUL 및 여러 바이트를 포함한 원본과 응답 본문이 정확히 같고 `Content-Length`는 실제 본문 바이트 수와 일치한다. 빈 파일은 200, 길이 0, 빈 본문을 확인한다.
- 임의의 한 내부 버퍼 크기에 의존하지 않는 충분히 큰 파일이 잘리지 않고 완전하게 제공된다. 구체적인 크기는 검증 범위 확정 시 정한다.
- 확장자 기반 MIME 정책이므로 파일 내용의 포맷 유효성 검사는 요구하지 않는다.

## 경로·접근·오류

- `/assets`와 `/assets/`는 각각 미등록 경로 및 디렉터리 요청으로 외부에 404를 준다. 다른 디렉터리도 목록이나 기본 파일을 제공하지 않는다.
- 심볼릭 링크 해석 후 최종 대상이 디렉터리·FIFO 등 일반 파일이 아닌 경우와 지원하지 않는 확장자는 제공하지 않는다. FIFO 검증은 서버가 멈추는 경우에도 테스트가 무기한 대기하지 않도록 테스트 클라이언트 측 제한시간을 둔다.
- `/assets/...` 경로 부분의 유효한 퍼센트 인코딩은 400이고, 잘못된 퍼센트 구문도 기존 파서 기준 400이다. 쿼리 인코딩과 다른 경로의 정책을 새로 가정하지 않는다.
- 고정된 파일 구성에서 `..`이 포함되어도 OS가 해석한 최종 대상이 `assets` 안이면 제공할 수 있고, 밖이면 제공하지 않는다. 클라이언트가 경로를 미리 정규화해 버리지 않는 입력을 사용해야 한다.
- 고정된 파일 구성에서 내부 심볼릭 링크가 가리키는 일반 파일은 허용하고, 외부 또는 형제 디렉터리를 가리키는 링크는 내용을 제공하지 않는다. 끊어진 링크는 404다. 경로 접두사만 비슷한 형제 디렉터리도 허용 영역과 혼동하지 않는다.
- 고정된 구성에서 `assets/link`가 `assets/sub/deep`를 가리킬 때 `link/../file`은 문자열 상쇄가 아닌 OS 해석 결과인 `assets/sub/file`을 가리킨다.
- **개인 정책:** 존재하지 않음, 접근 불가, 허용 영역 밖은 공통 404 상태·본문 및 의미 있는 응답 헤더의 일치를 확인한다. 시간 차이 등 다른 관찰 경로까지 구별 불가능하다고 보장하지 않는다. 접근 불가 사례는 실제 서버 프로세스 권한에서 재현 가능한지 확인한다.
- 예상하지 못한 서버 내부 오류는 500이다. 파일 전송 시작 후 실패는 새 HTTP 오류 응답을 붙이지 않고 불완전하게 중단·정리한다. 오류 분류가 미정인 사례는 기대 코드를 임의로 추가하지 않는다.

## 기존 HTTP 회귀 — 외부 동작 및 기존 단위 계약

- `/`, `/hello`, `/hello?x=1`은 기존 Hello를 반환한다. `/%68ello` 및 `/a/../hello`는 원본 경로 기준 미등록이다. 정적 파일의 경로 해석을 전역 라우팅에 적용하지 않는다.
- 기존 `GET /echo`는 405 및 `Allow: POST`, `POST /hello`는 405 및 `Allow: GET`, 미지원 `DELETE /hello`는 501이다.
- `POST /echo`는 바이너리·빈 본문의 길이와 내용을 보존한다. 현재 응답의 HTTP/1.1 및 `Connection: close` 정책을 유지한다.
- 단위 검증과 실제 서버 프로세스를 통한 기능·회귀 검증을 구분한다. 실행 명령과 결과는 이 기준이 아니라 별도로 기록한다.

## 라우트·본문 제공 계약

- 기존 `/`, `GET /hello`, `POST /echo`가 유지된다. Echo는 NUL을 포함한 본문과 빈 본문을 실제 바이트 그대로 반환한다.
- 라우팅 결과는 메서드와 경로가 모두 맞는 후보 중 가장 긴 경로다. 동률의 정확 일치는 접두사보다 우선하고, 동일 규칙 중복은 먼저 등록한 규칙이 우선한다.
- 405에서는 경로에 일치하는 정확·접두사 규칙 전체의 지원 메서드를 중복 없이 `Allow`에 반영한다. 예시용 겹침이 필요하면 테스트 데이터로 구성하고 실제 공개 라우트 추가를 강제하지 않는다.
- 겹치는 규칙을 확인할 때는 테스트에서 만든 규칙 목록을 사용할 수 있어야 한다. 실제 공개 라우트를 테스트 목적으로 추가하거나 특정 내부 함수를 공개하도록 강제하지 않는다. 규칙 목록을 테스트 대상에 전달하는 구체적인 방법은 별도로 판단한다.

### 내부 제공자 계약 — `send_body()`와 `send_prepared_response()`

- 이 절은 사용자가 정한 내부 제공자 계약이며 HTTP E2E에 특정 내부 함수명을 강제하지 않는다. 오류·잘못된 조각·호출 순서를 확인할 수 있도록 시험용 본문 제공자와 송신 결과를 전달하거나 재현하는 방법은 별도로 판단한다.
- `send_body()`는 `body_provider.next_func`가 돌려준 조각을 순서대로 전송하고, 현재 조각의 부분 송신을 완료한 뒤 다음 조각을 요청한다.
- 데이터 결과인데 위치가 NULL이거나 길이가 0이면 오류다. 제공자가 같은 버퍼를 재사용해도 현재 조각의 전송 완료 전에 다음 조각으로 덮이지 않는다.
- 제공자가 선언 길이보다 먼저 완료하거나 오류를 반환하면 불완전한 응답으로 중단한다. 조각이 남은 길이보다 길면 그 조각은 전송하지 않는다.
- 길이 0이면 제공자를 호출하지 않고, 선언 길이를 정확히 전송한 뒤에는 추가 호출하지 않는다. 전송 실패 후에도 다음 조각을 요청하지 않는다.
- `prepare_file()`의 준비 실패 시 준비 과정의 자원을 정리한다. 준비 성공 후 `send_prepared_response()`는 성공·실패·헤더 전송 실패·클라이언트 종료 경로에서 `body_provider.cleanup_func`가 있으면 정확히 한 번 호출한다. `NULL`도 허용한다. 준비 실패를 호출자에게 표현하는 방식은 미정이다.
- 제공자 정리는 본문 전송 직후 연결 종료 처리 전에 수행하며 전송 오류 정보를 덮지 않는다.
- `send_prepared_response()`를 호출해 헤더 송신 실패와 본문 송신 실패 각각에서 `body_provider.cleanup_func`가 정확히 한 번 실행되는지 확인한다. 시험용 제공자가 실제 전송 흐름에서 호출되도록 하고, 테스트가 `cleanup_func`를 대신 호출하지 않는다.
- `/echo` 등 제공자가 빌린 본문은 전송과 정리가 끝날 때까지 유효하다. 연결 종료와 파일·메모리 정리의 관찰 가능한 결과를 확인하되 내부 함수 분리 자체는 강제하지 않는다.

## 과정별 추가 경계 사례

### 라우트 선택과 요청 해석 — `select_rule()`, `path_matches_rule()`, `http_parse_request()`

- 경로가 같은 정확 일치·접두사 규칙에서 같은 메서드를 지원할 때 정확 일치가 선택된다. 동일 규칙이 반복되면 첫 규칙의 처리 대상이 선택된다.
- 서로 다른 길이의 접두사가 동시에 일치할 때 메서드까지 일치하는 가장 긴 후보가 선택된다. 더 긴 규칙의 메서드만 다르면 일치하는 짧은 후보를 선택한다.
- 경로에 일치하는 여러 규칙이 같은 메서드를 반복 제공해도 `Allow`에는 한 번만 나타난다. 일치하는 다른 메서드는 누락하지 않으며 순서는 강제하지 않는다.
- `/assets/...`로 분류된 경로에 유효한 인코딩이 포함되면 400이다. 원본이 `/assets/`로 시작하지 않는 인코딩된 접두사는 정적 라우트로 재해석하지 않는다. 쿼리의 인코딩만으로 정상적인 정적 경로를 거부하지 않는다.
- 잘못된 퍼센트 구문과 정상 경로에 붙은 쿼리를 각각 확인한다. `..` 해석은 정적 파일 대응에서만 적용하며 다른 라우트로 재분류하지 않는다.

### 파일 준비와 경계 — `prepare_file()`, `inside_directory()`

- 유효한 루트에 `assets`와 페이지 파일이 없는 상태에서도 시작할 수 있다. `/cafe`, `/menu`, `/assets/...` 각각의 부재 요청은 404이며 이후 기존 요청을 처리할 수 있다.
- 루트가 없거나 디렉터리가 아니거나 확인할 수 없을 때 시작 실패를 확인한다. 권한에 따른 실패는 서버와 같은 권한에서 실제 재현 가능한 경우에 검증한다.
- 확장자가 디렉터리 이름에만 있거나 파일명에 없을 때 MIME이 있다고 판단하지 않는다. 지원 확장자 뒤에 다른 확장자가 붙은 파일도 지원 대상으로 취급하지 않는다.
- 실제 일반 파일이라도 경계 밖 또는 접두사가 비슷한 형제 디렉터리에 있으면 제공하지 않는다. 내부 링크, 외부 링크, 끊어진 링크, 디렉터리·FIFO 대상은 각각 독립된 사례로 확인한다.
- 링크와 `..`이 함께 있을 때는 문자열 상쇄와 OS 경로 해석의 결과가 서로 다른 파일 구성을 사용해 OS 해석을 검증한다.
- 파일 대상 또는 경계 확인·열기 중 부재·접근 불가가 발생하면 개인 정책의 404를 확인한다. 예상하지 못한 내부 오류는 500으로 처리하며, 오류 분류가 미결정인 경우 상태를 임의로 확정하지 않는다.
- 파일을 연 뒤 일반 파일 확인이나 응답 준비가 실패하면 그 과정에서 확보한 FD·메모리가 남지 않는다. 실패 후에도 서버가 다음 요청을 처리할 수 있다.

### 본문 전송과 정리 — `send_response()`, `send_body()`, `send_prepared_response()`

- 바이너리·빈 파일·여러 조각이 필요한 파일에 대해 응답 본문과 선언 길이를 바이트 단위로 확인한다. 조각의 구체적 크기나 개수는 고정하지 않는다.
- 제공자가 유효한 조각을 여러 번 반환하면 순서대로 전송한다. 현재 조각의 부분 송신이 끝나기 전에 다음 조각을 요청하지 않으며, 같은 저장 공간을 재사용하는 제공자도 확인한다.
- 조기 완료·제공 오류·NULL 또는 길이 0인 데이터 조각·남은 길이보다 큰 조각은 각각 실패로 처리한다. 초과 조각은 전송하지 않고, 이미 응답이 시작됐다면 두 번째 HTTP 응답을 덧붙이지 않는다.
- 선언 길이가 0이면 `body_provider.next_func`를 호출하지 않는다. 선언 길이를 다 보냈거나 송신에 실패한 뒤에도 추가 조각을 요청하지 않는다.
- 헤더 전송 실패, 본문 전송 실패, 클라이언트 조기 종료에서도 `send_prepared_response()`는 준비된 제공자를 정리한다. `body_provider.cleanup_func`가 있으면 정확히 한 번, `NULL`이면 호출 없이 진행하며 원래 전송 오류를 보존한다.
- 응답 준비 중 실패한 경우 준비 단계에서 확보한 자원을 정리한다. 이때 실패를 표현하는 내부 방식이나 준비되지 않은 제공자의 호출 방식은 임의로 강제하지 않는다.
- 파일이 응답 길이 결정 후 짧아져 조기 EOF가 생기는 경우 불완전한 응답을 중단하고 정리한다. 길이 결정 후 커지는 경우 선언한 길이를 초과해 전송하지 않는다.
- 요청 본문을 빌리는 응답은 전송과 정리까지 본문이 유효하다. 빈 본문 및 NUL을 포함한 본문을 확인한다.
