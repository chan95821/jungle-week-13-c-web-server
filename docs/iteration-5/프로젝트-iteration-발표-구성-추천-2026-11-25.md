2. 터미널에서 조회 요청을 연속으로 보내 서버 식별자가 A와 B로 바뀌는 모습을 보여줍니다.
3. 여유가 있으면 조회 서버 하나를 내린 뒤에도 나머지 서버로 응답받는 모습을 보여줍니다.

발표 멘트:

> “기존 카페 페이지는 웹 서버가 직접 제공합니다. 반면 과제 제출 상태 조회는 같은 서버 주소로 요청하지만, Reverse Proxy가 뒤쪽 조회 서버 A 또는 B로 전달합니다.”
>
> “이 구현에서는 정상 요청을 라운드 로빈, 즉 순서대로 번갈아 분배합니다. 한 서버의 연결에 실패하면 요청을 보내기 전에 다른 서버로 한 번 우회합니다.”

**주의:** A·B 분산은 확인할 수 있지만, 이것만으로 처리량이 좋아졌다고 주장하면 안 됩니다. 개인 요구사항 문서에서도 분산과 성능 향상을 구분하고 있습니다.

# 4. 동시성 모델 비교 — 55초

| 모델 | 처리 방식 | 특징 |
|---|---|---|
| **순차 처리** | 한 요청을 마친 뒤 다음 요청 처리 | 이해하기 쉽지만, 느린 요청이 뒤 요청을 기다리게 할 수 있음 |

# 4. 동시성 모델 비교 — 50초

| 방식 | 요청 처리 방식 | 설명할 차이 |
|---|---|---|
| 순차 처리 | 한 요청이 끝나면 다음 요청 처리 | 느린 요청이 뒤 요청을 지연시킬 수 있음 |
| 연결별 스레드 | 각 연결을 별도 스레드가 담당 | 연결 증가에 따른 스레드 관리가 필요 |
| **현재 서버** | 고정 작업자 프로세스 + 작업자별 `epoll` | 한 연결이 대기하는 동안 다른 준비된 연결을 진행 |

### 발표 멘트

> “여러 연결을 처리하는 방법에는 순차 처리, 연결마다 스레드를 사용하는 방식, 이벤트 기반 방식 등이 있습니다.

> 저희 서버는 부모 프로세스가 연결을 받아 네 개의 작업자에게 배정하고, 각 작업자가 `epoll`로 여러 연결을 관리합니다. 한 연결이 백엔드 응답을 기다릴 때 다른 준비된 연결을 진행할 수 있는 구조입니다.”

| 방식 | 느린 요청이 있을 때 |
|---|---|
| 순차 처리 | 뒤 요청이 앞 요청의 완료를 기다릴 수 있음 |

> “순차 서버는 느린 요청 하나가 뒤 요청을 기다리게 할 수 있습니다. 연결마다 스레드를 둘 수도 있지만, 저희는 고정된 네 작업자 프로세스를 두고 각 작업자가 `epoll`로 여러 연결의 준비 상태를 관리하도록 구성했습니다.
