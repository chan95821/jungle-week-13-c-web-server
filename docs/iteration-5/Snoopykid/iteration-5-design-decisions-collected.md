## 1. 실행 구조와 책임

| 항목 | 선택 | 후보·근거·비용 |
|---|---|---|
| 동시성 모델 | A: 고정 프로세스 풀 + 각 작업자 epoll | B: 고정 스레드 + 각 스레드 epoll. C: accept 담당 + 제한 큐 + blocking 스레드 풀 대조군. A는 연결 메모리·장애 경계가 분리되나 IPC·공유 상태·자식 회수가 복잡하다. B는 상태 공유가 쉽지만 메모리 오류의 영향과 경쟁 조건이 크다. C는 기존 코드 재사용이 쉽지만 느린 요청이 작업자를 점유한다. 성능 우위는 미확정. |
| 연결 수락 | 부모가 accept 후 FD 전달 | 작업자가 상속한 공유 리스너에서 직접 accept하는 대안보다 명시적 분배가 가능하나 IPC·큐·소유권 관리가 추가된다. |
| 백엔드 선택 책임 | 작업자가 공유 메모리에서 직접 선택 | 부모에게 선택을 요청하는 IPC 왕복 대안은 채택하지 않음. 부모 병목을 줄일 가능성과 공유 잠금·복구 비용을 교환한다. |
| 공유 범위 | 전체 작업자 기준 상태 | 작업자별 순번은 간단하지만 서버 전체 교대·통계 의미가 달라진다. |
| 이벤트 모드 | epoll LT | ET의 EAGAIN까지 처리·재개 관리보다 부분 처리와 공정성 구현이 쉽다. Linux/WSL 구현이며 macOS 지원을 자동 보장하지 않는다. |
| 파일 I/O | 작업자당 보조 스레드 1개 + 제한 큐 | 별도 프로세스는 격리 대신 IPC·회수 비용, 이벤트 루프 직접 read는 단순함 대신 디스크 대기로 다른 연결 지연. 네트워크·공유 백엔드 잠금은 helper가 다루지 않는다. |
| CGI | 비동기 stdout·PID별 회수 | helper에서 실행 준비, fork 자식은 async-signal-safe 작업과 exec만 수행. 기존 블로킹 CGI를 이벤트 루프에서 그대로 실행하지 않는다. 다중스레드 fork 안전성과 종료 자식 회수가 비용이다. |

## 2. 공유 상태와 장애 복구

- fork 전 익명 공유 mmap을 만들고 상속한다. shm_open 및 독립 실행 프로세스 참여는 제외한다.
- process-shared robust mutex를 채택한다. 지원·초기화 실패를 확인한다. robust는 잠금 보유자 사망을 탐지하며 임의 메모리 손상 복구를 보장하지 않는다.
- 선택과 예약 증가는 같은 짧은 잠금 구간이다. 네트워크·파일 I/O는 잠금 밖이다.
- 구조 A인 공유 요청 원장 + 작업자별 기여분 + 전체 집계 + 제한된 복구 기록을 채택했다. 단순 카운터보다 메모리·기록 비용이 크지만 요청 단위 중복 완료·세대별 회수·부분 갱신을 판별한다.
- 잠금 밖 사망은 부모 waitpid 확인 후 해당 세대 예약 회수. 변경 중 사망은 undo/commit 기록으로 rollback 또는 완료 상태 보존. 복구자 사망도 재복구한다.
- 요청 ID·작업자 세대·예약 상태로 늦은 완료와 중복 감소를 막는다. PID/FD 번호만으로 구분하지 않는다.
- 복구 성공 조건은 백엔드 전체 진행 수 = 작업자 기여분 합 = ACTIVE 예약 수이며, 다른 작업자 상태가 보존되어야 한다.
- 신뢰할 수 없는 모순은 제한 진단을 남기고 전체 종료한다. 그럴듯한 값으로 함께 손상된 상태까지 탐지하지는 못한다.
- 진단은 작업자·세대·검사·복구 단계·종료 이유를 포함하되 요청 본문·민감 정보·무제한 메모리 덤프는 제외한다.
- 작업자 하나 사망 시 나머지는 계속 운영한다. 죽은 연결 복원·백엔드 작업 자동 재실행·자동 대체 worker 생성은 추가하지 않는다.

## 3. FD 전달·큐·감독

| 항목 | 결정 | 교환 비용·미채택 대안 |
|---|---|---|
| IPC | UNIX SOCK_STREAM + SCM_RIGHTS | 추천됐던 SEQPACKET의 메시지 경계 대신 직접 프레임·부분 I/O·FD 귀속을 관리한다. |
| 부모 FD 해제 | 전체 프레임 전송 완료 후 close, ACK 없음 | 수신/등록 ACK는 확인 가능성을 주지만 추가 IPC·타임아웃·FD 보관이 필요하다. 송신 성공은 등록/요청 완료 보장이 아니다. |
| 중복 전달 방지 | 첫 양수 sendmsg 이후 ancillary 재송신·다른 worker 자동 재배분 금지 | 일부 바이트만 보내도 FD는 전달됐을 수 있으므로 상태가 필요하다. |
| 수신 시작 | 전체 프레임 검증 후 client 처리 | 불완전·잘못된 프레임의 FD를 정리한다. |
| 대기열 | 부모 전역 미배정 FIFO | worker별 FIFO는 특정 느린 worker에 묶인다. 전송 시작 시 선택·worker 진행 수 증가. |
| 포화 | accept 일시 중단 | 계속 accept 후 즉시 close하는 비용을 피하나 커널 큐 지연/연결 실패가 가능하고 HTTP 503을 보장하지 않는다. |
| 종료 통지 | bounded CLOSED 큐 + 부모 연결 장부 | 공유 완료 원장 추가 대안보다 복구 상태가 적다. 부모는 CLOSED 전까지 점유로 계산하므로 적체 시 배정이 늦어진다. |
| 긴급 통지 | 별도 nonblocking pipe + worker별 고정 진단칸 | 기존 STREAM 포화로 긴급 통지가 밀리는 위험을 줄이나 pipe 포화·게시 중 사망 검증이 필요하다. |
| 시그널 | 최소 핸들러 + epoll_pwait | signalfd 대안은 FD와 Linux 전용 관리가 추가된다. ready I/O 중 시그널 지연 반례 후 반환 직후 잠깐 허용·재차단을 채택했다. |
| worker 이상 | 격리→TERM→유예 후 KILL→waitpid 후 회수 | 한 채널 오류에 전체 종료하는 대안보다 서비스 지속성이 있으나 감독 상태가 복잡하다. 전원 소실 시 오류 종료. |
| 잠금 경합 재시도 | pending일 때만 worker별 10ms 기한 | unlock 통지는 빠를 수 있지만 유실·사망·추가 IPC 비용이 있다. 다른 I/O로 깨어나도 기한 전 반복 시도하지 않는다. |

## 4. 분배 알고리즘과 측정 의미

worker 선택과 조회 백엔드 선택 모두 네 후보를 실행 설정으로 지원한다. 계산만 재사용하고 순번·진행 수·통계·설정은 분리한다. 최종 승자는 아직 선택하지 않았다.

| 후보 | 장점 | 한계 |
|---|---|---|
| RR | 단순한 순번 분배 | 작업 비용·속도 차이 미반영 |
| Least Outstanding + 동률 RR | 미완료 수 차이 반영 | 요청 하나의 무게와 CPU 사용량을 직접 알지 못함 |
| 응답 시간 + 동률 RR | 관측 지연 반영 | 오래된 값·선택 편향·초기 미측정·빠른 오류 처리 필요 |
| (진행 수 + 1) × 대표 시간 + 동률 RR | 개수와 시간 결합 | 지표 왜곡·오버플로우·복잡성, 최적 공식임을 보장하지 않음 |

- worker 진행 수: 배정 후 미종료 연결. 느린 헤더·본문·백엔드 대기·출력·정리 포함. HTTP 처리 중 요청만 세는 대안은 미채택.
- backend 진행 수: 선택·connect 시도 전 예약부터 최종 프레이밍 완료 또는 실패·취소까지. client 잔여 출력과 분리한다. client 종료까지 유지하는 대안은 느린 client를 backend 부하로 계산하는 문제가 있다.
- backend 시간: connect 직전부터 최종 본문·프레이밍 검증 완료까지. worker 시간: FD 인계 완료부터 연결 처리·자원 정리 완료까지. 헤더까지만 측정하는 대안보다 긴 본문 비용도 포함하지만 client 역압력의 영향도 섞인다.
- EWMA 계수 1/8. 미측정 대상끼리 RR. 오래된 값은 보존하고 시간/결합 정책은 32회마다 RR 탐색한다.
- 연결 실패·타임아웃 표본은 max(실제 시간, 1초). client 취소·worker 사망은 시간 표본 제외, 예약은 회수.
- 점수의 정확한 정수 동률은 RR, 곱셈은 포화 처리한다.
- worker-policy/query-policy를 설정에 각각 명시. 자동 정책 전환·재시도·장애 backend 제외는 추가하지 않는다.

## 5. 네트워크·역압력·자원 수명

- 연결당 응답 중계 16KiB, 가득 차면 backend 읽기 중단, 8KiB 이하에서 재개.
- FD당 64KiB 또는 syscall 16회 처리 후 다른 연결로 돌아간다. 공정성을 얻는 대신 재개 상태가 필요하다.
- 전체 기한은 유지한다. 의도적 역압력 중 backend 무진행 타이머만 정지한다.
- backend 선택 잠금 대기 1초 초과 503. 예약 해제 경합은 토큰을 보존하고 슬롯 재사용을 보류한다.
- 연결별 FD·버퍼·송수신 위치·기한을 소유한다. 기존 blocking 완료 대기 함수를 그대로 이벤트 루프에 넣지 않는다.
- 파일 helper는 연결당 한 작업만 수행하고 기존 16KiB provider 버퍼를 빌린다. 송신 후 다음 조각을 읽는다. 취소 중 작업이 끝나기 전 슬롯/provider/CLOSED를 해제하지 않는다.
- 실행 중 디스크 syscall은 강제 취소하지 않는다. helper join은 대기할 수 있고 부모 SIGKILL도 커널 D 상태의 즉시 회수를 보장하지 않는다.
- CGI는 nonblocking stdout·청크·역압력, PID별 WNOHANG 단일 회수자, 취소 TERM/기존 200ms 뒤 KILL. 자식 회수 전 슬롯 종료 통지를 보류한다. 응답 시작 후 새 HTTP 오류를 덧붙이지 않는다.

## 6. 임시 수치와 재검토·실험 목록

| 수치 | 초기값·의미 |
|---|---|
| worker | 4개; 1·2·4·8 비교 후보 |
| 부모 FIFO | 128 |
| worker 연결 상한 | 256 |
| 전체 연결 상한 | 1,152 |
| backend 예약 슬롯 | 1,024 |
| 공유 매핑 예산 | 1MiB; 전체 서버 메모리 한도가 아님 |
| CLOSED 큐 | worker당 최대 256 |
| 종료 유예 | 2초; 종료 완료 보장 시간이 아님 |
| pending 잠금 재시도 | 10ms |
| 중계 버퍼/읽기 재개 | 16KiB / 8KiB |
| 처리 예산 | FD당 64KiB 또는 16 syscall |
| 선택 잠금 대기 | 1초 후 503 |
| EWMA/탐색/실패 floor | 1/8, 32회, 1초 |
| 파일 helper | worker당 1개, 최적 수 아님 |

위 수치는 표준 권장 최적값이나 성능 실측 결론이 아니다. 연결 1만 개는 검토 목표이며 현재 상한에서 달성했다고 주장하지 않는다. WSL ABI의 공유 매핑 33,528바이트 등 모듈별 비용은 기존 review 문서에 있으며 총 RSS·커널 소켓 메모리와 다르다.

동일 환경·빌드·요청·backend·기한·상한에서 정상/느린 backend/서로 다른 비용/장애/회복을 비교한다. worker 정책과 backend 정책을 동시에 바꾸어 하나의 효과로 해석하지 않는다. 성공 처리량, p50/p95/p99, 실패·timeout, A/B 분포, 회복, CPU·메모리·FD·IPC·잠금 비용 및 구현·검증 비용을 고려한다. 앞선 대화의 16GB 노트북 자원 제약도 고려한다. GPU 사용은 본 서버 설계에서 채택한 바 없다. 성능 측정은 조건·지표 제시 후 별도 허락이 필요하다.

## 7. 최신 구현 상태와 남은 사항

최신 구현 세션 보고는 제품 main이 부모 1개·worker 4개·worker별 epoll로 통합됐으며 파일 helper와 CGI까지 최소 확인을 마쳤다는 것이다. 이 문서 작성에서 재실행한 결과는 아니다. 초기 문서의 ‘main 순차/미통합’은 역사 기록이다.

중간 단위 ASan/UBSan 검증 후 사용자는 ‘구현 우선, 중간은 컴파일·링크와 직접 필요한 최소 확인, 전체 회귀·광범위 장애는 통합 체크포인트’로 변경했다. 따라서 최종 전체 회귀·광범위 장애·성능 측정이 완료됐다고 볼 수 없다.

남은 후보: 최종 분배 정책 선택과 임시값 튜닝, 전체 통합 회귀·장애 검증, stdout EOF 후 살아 있는 CGI의 별도 종료 기한, worker 강제 사망 시 후손 감독. 자동 대체 worker·반복 장애 재시작 제한은 구현 확정으로 해석하지 않는다. 인증·캐싱·복수 물리 프록시 운영은 Q&A 개념 설명이며 Iteration 5 구현 선택이 아니다.

```text
    → send_prepared_response()
       → 본문 전송 완료까지 대기
```

이를 다음 구조로 전환할 계획입니다. 아래 함수명은 설계용 이름입니다.

```text

 → 설정·리스너 준비
 → start_workers()
    → run_worker_event_loop()
       → 준비된 연결 확인
       → advance_connection()
          → 헤더·본문 수신
          → 기존 파서·라우팅
          → 로컬 응답 준비 또는 백엔드 연결·중계
          → 부분 송신
          → 완료·오류·기한 초과 시 자원 정리
```

- 연결·버퍼·백엔드 FD의 프로세스별 소유권
- 조회 순번과 백엔드 상태를 프로세스끼리 공유할 필요와 비용

**강점은 장애 경계가 명확하다는 것이고, 비용은 프로세스 사이 상태 공유와 관리입니다.**



**B. 고정 스레드 작업자 + 스레드별 이벤트 루프**
```

 ├─ 관리 스레드
 ├─ worker 스레드 1 → 이벤트 루프 → 여러 클라이언트·백엔드
 ├─ worker 스레드 2 → 이벤트 루프 → 여러 클라이언트·백엔드
 └─ …
```

연결 하나를 특정 worker에 귀속시킵니다. 같은 주소 공간을 사용하더라도 연결별 상태를 모든 스레드가 함께 수정하지 않도록 합니다. Envoy도 연결의 수명 동안 한 worker가 담당하는 구조를 사용합니다. [Envoy 스레딩 모델](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/intro/threading_model)

| 선택 흐름 | 작업자가 선택 요청 → 부모가 선택·예약 → 결과 전달 | 작업자가 잠금 → 선택·예약 → 잠금 해제 |
| 완료 처리 | 작업자가 부모에게 완료·실패 통보 | 작업자가 공유 상태를 직접 갱신 |
| 동기화 비용 | 요청별 IPC 왕복·메시지 처리 | 잠금 경쟁·공유 메모리 접근 |
| 작업자 장애 | 부모가 해당 작업자의 미완료 기록 회수 | 작업 중 끊긴 갱신과 예약 기록 복구 |
| 주요 한계 | 부모가 분배 병목·전체 장애 지점 | 복구·일관성 검증이 복잡함 |

**현재는 ①을 추천합니다.** 이미 부모가 연결을 수락하므로, 분배 상태도 부모 한 곳에서 변경하면 네 후보를 같은 관리 구조로 비교하기 쉽습니다. 성능 우위가 확인됐다는 뜻은 아닙니다.

①의 흐름은 다음과 같습니다. 함수명은 설계용입니다.

```text
부모 main()
 → accept()
 → dispatch_client_fd()          작업자에게 연결 전달

작업자 이벤트 루프
 → 요청 수신·검증·라우팅
 → request_backend_selection()   부모에게 조회 목적지 요청
 → 다른 연결 처리                선택 결과를 기다리며 블로킹하지 않음

부모 이벤트 루프
 → select_and_reserve_backend()  알고리즘 실행 + 진행 요청 예약
 → 작업자에게 선택 결과 전달

작업자
 → 백엔드 연결·송수신
 → report_backend_result()       완료·실패 통보

부모
 → release_backend_reservation() 예약 해제
 → 합의된 정책에 따라 시간 통계 반영
```

작업자 장애 회수는 **작업자 세대 번호 + 요청 ID + 선택한 백엔드**를 부모가 기록하는 방안을 제안합니다. 작업자가 종료되면 남은 예약만 한 번 회수하고, 이미 처리한 완료 통보나 이전 세대의 통보는 다시 반영하지 않습니다. **작업자 종료를 응답 시간 통계에 어떻게 반영할지는 별도 결정**입니다.

②에서도 같은 예약 기록이 필요합니다. 잠금 소유자 사망을 감지하는 robust mutex가 있어도, 중간에 끊긴 데이터 갱신까지 자동 복구해 주지는 않습니다. [Linux robust mutex 문서](https://man7.org/linux/man-pages/man3/pthread_mutexattr_setrobust.3.html)

Iteration 1의 I/O 모델을 선택해주세요. 블로킹 순차 처리는 accept→수신→송신을 연결 하나씩 따라가기 쉽지만 느린 클라이언트가 다음 연결 처리를 지연시킵니다. non-blocking 이벤트 루프는 여러 연결을 관리하지만 연결별 상태와 이벤트 처리를 지금 구현해야 합니다.\
\
1\. 블로킹·한 번에 한 연결 처리, 동시성은 5단계에서 도입 (추천)\
2\. non-blocking·이벤트 루프를 1단계부터 도입

I/O 모델이 더 있으면 알려주고, 지금 말로는 장단점이 잘 안와닿아.


**당시 답변**

**지금은 1번을 추천해. 다만 ‘블로킹이면 한 번에 한 연결만 처리한다’는 뜻은 아니야. 블로킹 소켓을 쓰면서 스레드나 프로세스로 여러 연결을 동시에 처리할 수도 있어.**

선택지에는 두 가지 결정이 묶여 있어.

- **I/O 방식**: 데이터를 당장 읽거나 쓸 수 없으면 기다릴 것인가?
- **동시성 방식**: 여러 클라이언트를 누가, 어떻게 나눠 처리할 것인가?

예를 들어 보자. **A는 서버에 연결한 뒤 요청을 보내기까지 10초를 기다리고, B는 바로 요청을 보내는 상황**이야.

**① 블로킹·순차 처리 — A를 끝내고 B를 처리**

```text
서버: A 연결 수락 → A의 데이터를 10초 기다림 → A 응답 → B 처리
```

`recv()`에서 기다리는 동안, 같은 실행 흐름은 다음 클라이언트를 처리하지 못해. B의 TCP 연결 자체는 운영체제의 대기 큐에 들어갈 수 있지만, 서버 프로그램의 처리는 지연돼.

장점은 코드 흐름이 직선이라는 거야.

```text
연결 수락 → 요청 읽기 → 응답 보내기 → 연결 닫기 → 반복
```

디버거로 한 줄씩 따라가기 쉽고, 소켓과 HTTP 동작을 배우기에 좋아. 단점은 **한 명이 느리면 뒤의 사람도 기다린다**는 점이야.

**② 블로킹·멀티스레드 — A를 기다리는 동안 다른 스레드가 B 처리**

```text
연결 수락 담당 → A를 작업자 1에게 전달
             → B를 작업자 2에게 전달

작업자 1: A의 데이터를 기다림
작업자 2: B의 요청 처리 → 응답
```

각 작업자는 블로킹 방식으로 읽고 써도 돼. 그래서 기존의 “요청 읽기 → 응답 보내기” 코드를 비교적 많이 재사용할 수 있어.

대신 작업 분배와 공유 데이터의 동기화가 필요해. **스레드 풀**은 작업자 수를 미리 정해 두는 방식인데, 모든 작업자가 느린 클라이언트를 기다리게 되면 새 요청도 대기해. 스레드는 같은 프로세스의 메모리를 공유해. [pthreads 매뉴얼](https://man7.org/linux/man-pages/man7/pthreads.7.html)

**③ 블로킹·멀티프로세스 — 연결별로 별도 프로세스가 처리**

`fork()`로 자식 프로세스를 만들어 A와 B를 각각 처리하는 방식이야.

스레드보다 메모리 공간이 분리되어 공유 데이터 충돌은 줄지만, 프로세스 생성·종료 관리와 소켓 닫기, 자식 프로세스 회수가 필요해. 연결마다 프로세스를 만드는 방식은 연결 수가 늘수록 자원 부담이 커져.

**④ non-blocking·이벤트 루프 — 준비된 연결부터 조금씩 처리**

```text
서버: A 연결 수락 → 아직 데이터 없음 → A 상태를 기록
     B 연결 수락 → 데이터 있음 → B 처리·응답
     나중에 A 데이터 도착 → A 처리 재개
```

`select`, `poll`, `epoll` 같은 기능으로 읽거나 쓸 준비가 된 연결을 확인해. 준비된 연결이 없으면 이벤트 대기 함수에서 잠들 수 있으므로, 계속 반복하며 CPU를 쓰는 방식은 아니야. [epoll 매뉴얼](https://man7.org/linux/man-pages/man7/epoll.7.html)

장점은 **소수의 스레드로 많은 연결의 네트워크 대기를 관리하기 좋다**는 거야. 대신 연결마다 다음 정보를 직접 보관해야 해.

```text
A: 헤더를 30바이트 받음, 나머지를 기다리는 중
B: 응답 1,000바이트 중 600바이트 전송, 나머지를 기다리는 중
```

즉, “한 연결을 끝까지 처리하는 함수”에서 **“연결별 진행 상황을 저장하고 이어서 처리하는 구조”**로 바뀌어. 이벤트 루프 안에서 오래 걸리는 계산이나 블로킹 작업을 하면 다른 연결도 지연될 수 있어.

| 방식 | 이해·구현 부담 | 느린 클라이언트의 영향 | 이번 프로젝트에서 적절한 시점 |
|---|---|---|---|
| 블로킹·순차 | 가장 작음 | 다음 연결 처리도 지연 | Iteration 1 |
| 블로킹·스레드 풀 | 중간 | 작업자 하나를 점유 | 5단계 동시성의 유력한 선택 |
| 블로킹·멀티프로세스 | 중간 | 프로세스 하나를 점유 | 프로세스 모델을 배우고 싶을 때 |
| non-blocking·이벤트 루프 | 초기 부담이 큼 | 대기 중인 연결을 두고 다른 연결 처리 가능 | 이벤트 기반 구조를 목표로 할 때 |

이번 요구사항은 동시성 방식 중 **하나 이상**을 선택하면 되므로, non-blocking이 필수는 아니야.

**현재 6단계 계획대로라면, 1단계는 블로킹·순차 처리로 시작하고 5단계에서 스레드 풀을 도입하는 경로가 자연스러워.** 지금은 연결 하나를 처리하는 함수 안에 요청 버퍼와 처리 상태를 두고, 전역 변수에 섞어 놓지 않는 정도면 충분해.

반대로 **최종 목표를 `epoll` 이벤트 루프로 이미 정했다면**, 1단계부터 도입하는 것도 타당해. 나중에 전환할 때는 단순 옵션 변경이 아니라 수신·송신 흐름을 연결별 상태 기반으로 바꾸는 작업이 필요하기 때문이야.

**당시 답변**

**요구사항상 최종 서버에는 동시성이 필요하지만, non-blocking이나 이벤트 루프까지 반드시 구현할 필요는 없어.** `fork`, 스레드 풀, 이벤트 루프 중 하나를 구현하고, 왜 선택했는지 실험으로 설명하면 돼.

이번에는 **“느린 클라이언트나 느린 백엔드가 있을 때 다른 요청이 얼마나 지연되는가”**를 중심으로 비교하는 게 좋아. 프록시가 필수라서, 단순히 고정 응답을 빨리 보내는 성능보다 이 문제가 중요해.

### 먼저 선택할 사항

| 선택 | 얻는 것 | 감수할 것 | 추천 |
|---|---|---|---|
| Forward Proxy / Reverse Proxy | Forward는 목적지 호스트 해석·중계 학습, Reverse는 경로 라우팅·백엔드 관리 학습 | Forward는 다양한 외부 서버, Reverse는 라우팅 설정과 백엔드 장애 처리 | **Reverse Proxy 먼저** |
| Linux·WSL 전용 / macOS까지 지원 | 전용이면 `epoll` 등 Linux 기능 사용 가능, 공통 지원이면 이식성 확보 | 공통 지원은 API 선택·플랫폼별 검증 증가 | **실제 제출·팀 환경에 맞춰 선택** |
| 연결당 요청 하나 / keep-alive 지원 | 하나면 연결 수명과 자원 정리가 단순, keep-alive면 연결 재사용 | keep-alive는 요청 반복 처리·유휴 연결·메시지 경계 관리 증가 | **초기는 `Connection: close`, 이후 지원 범위 결정** |
| 동시성 모델 | 아래 실험으로 결정 | 구현 복잡도·자원·장애 격리 사이의 선택 | **지금 확정하지 않고 실험** |

keep-alive는 요구사항에 의미와 처리가 학습 항목으로 있으므로, 영구적으로 제외했다고 단정하면 안 돼. 초기 구현에서는 연결 종료 방침을 명확히 하고, 최종 지원 범위를 기록하는 게 좋아.

### 동시성 모델에서 실제로 교환하는 것

“A는 연결만 하고 요청을 늦게 보내고, B는 정상 요청을 보낸다”고 생각해 보자.

| 모델 | A가 느릴 때 B는? | 구현에서 추가되는 일 | 중요한 한계 |
|---|---|---|---|
| 블로킹·순차 | A 처리가 끝날 때까지 기다림 | 가장 적음 | 최종 동시성 요구 충족용으로는 부족 |
| 연결마다 `fork()` | 다른 자식 프로세스가 B 처리 | 자식 회수, FD 정리, 프로세스 수 제한 | 느린 연결마다 프로세스가 남음 |
| 블로킹·스레드 풀 | 남는 작업자가 B 처리 | 작업 큐, 동기화, 스레드 종료 | 작업자가 모두 기다리면 B도 대기 |
| non-blocking·이벤트 루프 | A를 대기 상태로 두고 B 처리 | 연결별 버퍼·진행 상태, 부분 송수신, 이벤트 등록 | 루프에서 오래 걸리는 작업을 하면 전체 지연 |
| 여러 프로세스 × 스레드 풀 | 다른 작업자가 B 처리 | 프로세스와 스레드의 관리가 모두 필요 | 총 작업자가 모두 점유되면 역시 대기 |

**프로세스와 스레드를 함께 쓰는 블로킹 서버도 가능해.** 예를 들어 프로세스 2개에 스레드 4개씩 두면 작업자는 총 8개야. 하지만 느린 연결 8개가 전부 차지하면 다음 요청은 기다려. 혼합 모델 자체가 블로킹 대기 문제를 해결해 주지는 않아.

반대로 이벤트 루프도 항상 빠른 것은 아니야. 많은 연결이 기다리는 상황에서는 유리하지만, 적은 연결로 짧은 요청을 처리할 때는 추가 구현 비용에 비해 이점이 작을 수 있어.

### 30분 실험은 이렇게 하자

**다섯 모델을 처음부터 직접 구현하는 시간까지 포함하면 30분은 빠듯해.** 비교용 서버와 측정 스크립트를 먼저 준비하고, 네가 실행·관찰·판단하는 시간을 30분으로 잡는 게 현실적이야.

비교 코드는 본 서버와 별도 실험 폴더에 두고, 다음 조건을 동일하게 맞추면 돼.

- C·POSIX 소켓으로 구현하고, 고정된 작은 HTTP 응답을 반환.
- 연결당 요청 하나, 응답 후 종료.
- 요청 크기 제한·동일한 타임아웃 적용.
- 순차 / 연결당 fork / 스레드 풀 8개 / `poll` 이벤트 루프 / 프로세스 2개 × 스레드 4개 비교.
- `poll`을 쓰면 Linux와 macOS에서 공통으로 실험하기 쉬움. 이후 Linux 전용으로 정하면 `epoll` 검토.

| 시간 | 실험 | 확인할 것 |
|---|---|---|
| 0–5분 | 빌드하고 모델별 정상 응답 확인 | 비교 코드 자체가 정상인지 |
| 5–10분 | 정상 요청, 동시 연결 1·8·32개 | 처리량, 지연, 실패 수 |
| 10–18분 | 요청 헤더를 끝내지 않는 연결 8개를 먼저 열고 정상 요청 추가 | 느린 연결이 정상 요청을 막는지 |
| 18–25분 | 별도 테스트 백엔드가 1초 뒤 응답하도록 하고 프록시 요청 실행 | 백엔드 대기로 작업자가 묶이는지 |
| 25–30분 | 결과와 코드 비교 | 성능 이득에 비해 구현 부담이 적절한지 |

세 번째 실험이 가장 직관적일 거야.

```text
느린 연결 8개를 먼저 유지한 상태에서 정상 요청 1개 추가

순차 서버       → 앞선 연결을 기다림
스레드 풀 8개   → 모든 작업자가 점유되면 기다림
fork 서버       → 제한 내에서 새 자식이 처리 가능
이벤트 루프     → 느린 연결을 보관하고 정상 요청 처리 가능
2프로세스×4스레드 → 작업자 8개가 점유되면 기다림
```

여기서 fork가 잘 나온다고 “fork가 가장 우수하다”고 결론 내리면 안 돼. 대신 더 많은 프로세스를 사용했을 수 있으니 **프로세스·스레드 수와 메모리도 함께 봐야 해.** 메모리는 fork의 공유 페이지 때문에 RSS 합계만으로 단순 비교하지 않는 게 좋아.

측정 결과는 이 정도면 충분해.

| 모델 | 정상 요청 처리량 | 느린 연결이 있을 때 정상 요청 지연 | 실패·타임아웃 수 | 자원 사용 | 구현·디버깅 부담 |
|---|---:|---:|---:|---|---|
| 순차 / fork / 스레드 풀 / 이벤트 루프 / 혼합 | 측정 | 측정 | 측정 | 관찰 | 코드 비교 |

**이 실험으로 확인할 수 있는 것은 작은 부하에서의 대기 특성과 구현 비용이야. C10K 대응이나 운영 환경의 우열까지 입증하는 실험은 아니야.**

내 초기 추천은 **Reverse Proxy + 블로킹 스레드 풀**이야. 다만 실험에서 느린 연결·백엔드 대기 때문에 정상 요청이 크게 밀리고, 그 상황을 프로젝트의 주요 목표로 삼고 싶다면 이벤트 루프를 선택할 근거가 생겨. 혼합 모델은 단일 프로세스의 스레드 풀보다 얻는 이점이 확인될 때 선택하면 돼.

**2. 동적 요청 처리 — 최신 Issue #3에는 명확히 추가돼 있음**

[Issue #3](https://github.com/chan95821/jungle-week-13-c-web-server/issues/3)의 현재 제목은 **“정적 파일 서빙 + 동적 요청 처리”**이고, 본문에도 다음이 있어.

입력을 바꾸면 응답도 달라지는지 검증하는 완료 조건까지 있어. **네가 걱정한 동적 처리 부분은 현재 Issue에는 들어 있어.**

| 단계 | 동적 처리 역할 |
|---|---|

CGI는 원문에서 제시한 예시라서 별도로 꼭 구현할 필요는 없어. 백엔드 전달은 [Issue #4](https://github.com/chan95821/jungle-week-13-c-web-server/issues/4)에 계획돼 있어.

- 실제 엔드포인트와 입력·출력 형식

**복잡한 애플리케이션이나 DB까지 추가할 필요는 없어.** 작은 핸들러 하나에 정상·실패 기준을 명확히 두면 돼.

프록시가 두 개로 나눠진다는 의미는 현업에서 보통 컴퓨터(혹은 프로세서)가 나뉘는 거지? 프로세스가 나뉘는 게 아니라?


**당시 답변**

**둘 다 가능합니다. “프록시 2개”라는 말만으로 컴퓨터가 2대라는 뜻은 아닙니다.** 제가 앞서 그린 그림에서는 독립적으로 요청을 받는 프록시 실행 단위 2개를 뜻했습니다.

여기서 **프로세서와 프로세스**를 구분하면 이해하기 쉽습니다.

- **프로세서(CPU)**: 프로그램의 명령을 실행하는 하드웨어
- **프로세스**: 실행 중인 프로그램. 프록시 프로그램을 두 번 실행하면 별도 프로세스 두 개가 될 수 있음

배치는 다음처럼 나뉩니다.

| 구성 | 얻는 효과 | 한계 |
|---|---|---|
| 컴퓨터 1대에 프록시 프로세스 여러 개 | 여러 CPU 코어 활용, 프로세스 장애 분리 | 컴퓨터가 꺼지면 모두 중단 |
| 컴퓨터 여러 대에 프록시 배치 | 전체 자원 증가, 컴퓨터 한 대의 장애에 대응 | 앞단 분산과 여러 서버 운영 필요 |
| 한 프록시 안에서 여러 스레드 사용 | 여러 작업을 동시에 처리 | 같은 프로세스의 메모리와 장애 영향 공유 |

현업에서는 **여러 컴퓨터나 VM에 프록시를 배치하고, 각 프록시 내부에서도 여러 프로세스·스레드 또는 이벤트 루프를 사용하는 조합**이 가능합니다. 컨테이너가 두 개여도 같은 컴퓨터 위에서 실행 중일 수 있습니다.

따라서 구분할 질문은 두 가지입니다.

> **어디에 배치했나?** 같은 컴퓨터인가, 다른 컴퓨터인가?  
> **어떻게 동시에 처리하나?** 프로세스인가, 스레드인가, 이벤트 루프인가?

우리 프로젝트의 Iteration 5에서 고를 동시성 모델은 주로 **두 번째 질문**입니다. 노트북 한 대에서도 충분히 구현하고 비교할 수 있습니다.
