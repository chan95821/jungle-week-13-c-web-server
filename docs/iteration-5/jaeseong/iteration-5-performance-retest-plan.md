# B 현재 코드 성능 재측정·추가 측정 계획

2026-11-25 사용자가 “다시 하고 몇개 더 성능 측정을 위한 테스트 해보고 결과 넣어줘”라고 요청했다. 가독성 리팩토링 이후의 소스를 격리 빌드해 측정한다. 이전 보고서와 원시 데이터는 보존한다.

## 확정: 기존 조건 재측정

기존에 확정한 30회와 같은 조건이다. 이번 요청으로 현재 코드에 대한 재실행을 승인받았다.

- C 프록시 1개, 네트워크 작업자 4개·파일/CGI 보조 2개. C 제출 백엔드 1개·동일한 조회 백엔드 2개.
- 제출은 1KiB 바이너리 POST, 10건/초. 조회는 고정 13B 상태, 50·100·200·400·800건/초.
- B와 백엔드 직접 요청을 같은 조건으로 각각 3회. 각 시행은 준비 3초·측정 15초, 새 서비스 프로세스.
- 요청 예정 시각 기준 제한 2초, 생성기 미완료 요청 상한 256개. 새 연결마다 한 요청 후 SHUT_WR와 응답 EOF 확인.
- 기존 Python asyncio 생성기, GCC `-O2 -pthread`, 현재 사용할 수 있는 Debian WSL2. OS 한도·서버 정책·버퍼를 변경하지 않는다.
- 성공 처리량(req/s), 제출 p95(ms), 제출·조회 실패율(%), 실제 시작 기준 지연·생성 지연, RSS(MiB)·FD(개)를 기록한다. 준비 구간 실패와 측정 구간 실패를 분리한다.

위 30회는 완료했다. 측정 144,000건·준비 28,800건 모두 성공했고 전후 FD 변화는 없었다. [실측 결과](iteration-5-performance-retest-results.md)에 반복별 범위와 원본 자료를 기록했다. 아래 추가 범위의 선택 대기 상태는 유지한다.

## 추가 범위: 사용자 선택 대기

AGENTS.md의 “추가 측정이나 조건 변경도 다시 확인받는다”에 따라 아래 제안은 아직 실행 허락으로 간주하지 않는다. 기존 재측정과 독립적으로 제안했다.

| 묶음 | 변경하는 조건 | 유지하는 조건 | 추가 시행 수 | 목적 |
|---|---|---|---:|---|
| 높은 조회 부하 | 조회 1,600·3,200건/초 | 작업자 4, POST 1KiB/10건·초, B/직접 비교 | 12 | 기존 최고 부하보다 높은 구간의 실패·지연·생성기 제한 관찰 |
| 작업자 수 | 네트워크 작업자 1·2·8개 | 조회 800건/초, POST 1KiB/10건·초, B만 | 9 | 같은 부하에서 작업자 수에 따른 차이 관찰. 4개는 이번 기본 측정 결과 재사용 |
| 큰 제출 본문 | POST 64KiB | 작업자 4, 조회 800건/초, 제출 10건/초, B/직접 비교 | 6 | 본문 상한에서 제출 지연과 조회 처리량 관찰 |

추가 묶음도 준비 3초·측정 15초·3회, 요청 제한 2초·미완료 상한 256개, 같은 백엔드·빌드 옵션을 사용한다. 전체 추천안은 기본 30회+추가 27회다. 선택 전 추가 조건에 의존하는 계측 구현이나 부하 실행은 하지 않는다.

## 결과 해석과 보존

- 측정 중 다른 빌드·검증·성능 시행을 병행하지 않는다. 소스/생성기/바이너리 SHA256, 환경, 빌드 로그, 반복별 요약과 요청별 압축 CSV를 보존한다.
- 실패·상한 거절·생성 지연을 숨기지 않는다. 실패율 분모는 예정 요청 전체이며 타임아웃을 포함한다. 성공 지연만으로 실패가 많은 구간을 평가하지 않는다.
- 백엔드 직접 요청은 같은 WSL·Python 생성기 조건의 참고값이다. 프록시 병목·백엔드 병목·생성기 병목의 원인을 데이터 없이 확정하지 않는다.
- 작업자 수 비교는 B 내부의 차이이며 A/C와의 비교나 동시성 도입 전후 효과가 아니다. 고정 요청률을 소화했다고 최대 처리량을 측정했다고 표현하지 않는다.
- 이전 성능 보고서는 별도로 보존한다. 이번 결과는 새 Markdown 보고서로 작성하고 기존 결과 문서에서 링크한다. 성능 결과에 따른 서버 최적화나 다음 단계 구현은 하지 않는다.
