# B 성능 측정 제안 — 아직 실행하지 않음

이 문서는 측정 실행/벤치마크 구현 허락이 아니다. 팀 채택용 공통 조건도 아직 확정되었다고 가정하지 않는다.

- 목적: B 구현에서 조회 부하가 증가할 때 조회 성공 처리량과 제출 지연·실패율을 함께 확인한다. 다른 후보 우열이나 동시성 전후 효과를 이 결과만으로 주장하지 않는다.
- 환경: 현재 사용할 수 있는 Debian 13 WSL2, GCC `-O2 -pthread`, 네트워크 작업자 4개 + 로컬 I/O 보조 2개, 프록시 1 / C 제출 백엔드 1 / 같은 C 조회 백엔드 2 / 같은 WSL의 부하 생성기. 실제 CPU/RAM/커널/FD 한도는 실행 전에 기록한다. 기존 Ubuntu 실행 결과가 아니다.
- 요청: POST `/api/submissions`, 바이너리 본문 1024B, 초당 10개 고정. GET `/api/submission-status`, 동일 고정 상태, 조회 초당 50/100/200/400/800개. 새 TCP 연결마다 한 요청, Connection close.
- 도구 후보: Python 표준 asyncio의 일정 요청률 생성기(서버/백엔드는 C), 실제 송신 전에 생성 예정 시각을 기록한다. 최대 미완료 요청 256개. 제때 생성하지 못한 요청도 실패/지연에 반영하여 부하 생성기 포화를 숨기지 않는다.
- 조건당 준비 3초 + 측정 15초, 3회 반복, 조건별 중앙값을 비교한다. 요청 타임아웃 2초, 실패에 포함한다. 시간 경계에서 시작한 요청의 완료를 별도로 기다린다.
- 지표: 조회 성공 req/s, 제출 p95 ms, 제출/조회 실패율 %, 제출/조회 offered·started·success·timeout·생성 지연 개수, 프로세스 RSS MiB·열린 FD 수. 잠정 상한: 제출 p95 100ms, 각 실패율 1%. 이 상한은 팀 합의 전 개인 검토 기준이다.
- 백엔드 직접 요청에도 같은 부하와 반복 조건을 적용해 병목 참고값을 수집하는 것을 제안한다. 현재 C 백엔드 프로세스는 순차 처리이므로 백엔드 포화가 프록시 차이를 가릴 수 있다. 모든 후보에서 같은 코드/설정을 사용할 때만 공정한 비교가 된다.
- 이번 범위에서 제외: 워커 수/버퍼 변경 비교, 1개 vs 2개 조회 서버, 동시성 도입 전후, 10,000연결, 이종 용량 반례, 성능 결과에 따른 자동 튜닝.

측정 시 다른 검증·컴파일을 동시에 실행하지 않는다. 상한을 넘으면 그대로 보고하고, 구현/측정 조건 변경은 별도 사용자 결정으로 남긴다.
